# Research Index

- Maintainer: `@analyst` (Atlas). Created: 2026-10-22. Built from the notes already in the repo; no new web research was done for this index.
- Labels used inside the notes: **VERIFIED** (official source or repository code), **PARTIAL** (incomplete or secondary source), **UNVERIFIED** (inference, not confirmed).

## Owner golden rule (2026-10-22)

If the `@analyst` has already researched a topic and judged that no more research is needed, nobody spends tokens researching it again. This index makes the rule usable.

## How to use

1. Before dispatching research, the agent or the coordinator checks this index **and** the `@analyst` agent memory (`.claude/agent-memory/aiox-analyst/`).
2. Research is requested **only** for a **GAP**, for a **REFRESH IF** whose trigger has fired, or when `Review after` has passed (then only the **delta** since `Verified on` is researched). Name the row and the reason in the request.
3. When a row is **SUFFICIENT** and inside its term, consumers read the note (and its pt-BR copy) and cite it. They do not ask for new research.
4. Agents without web tools (`@po`, `@data-engineer`, `@dev`, `@qa`, `@ux-design-expert`) read the notes instead of asking for new research. If a note cannot answer their question, they escalate to the coordinator with the exact question. The coordinator then decides whether it is a real GAP.
5. The `@analyst` updates this index (en and pt-BR) every time a research note is created, refreshed or retired, and fills the dates and the term (below).
6. A note is desk research. It never replaces a test in the project environment (PostgreSQL, browser, real Twitch, OBS/CEF). A GAP that only a live test can close goes to `@qa`/`@dev` as a test task, not as web research.

## Dates and terms (owner decision, 2026-11-18)

- Every row has **Verified on** and **Review after**. Default term: **3 months** (`STD`). Volatile topics (Twitch APIs, package versions, security, moving products, game patches) use `VOL`: **6 weeks** and a review **before** the term when a trigger fires (changelog, deprecation, advisory). Class and reason are in the row.
- Up to the term: reuse, do not search again. Past the term: search only the delta since `Verified on`, then renew both dates. GAP or fired trigger: search right away.
- An overdue row needs a dated waiver in the last column (`until YYYY-MM-DD: reason`, at most 30 days after `Review after`). The CLI `npm run research:stale` warns (default) and gates with `--strict` in a weekly job; the contract test checks the format without the clock (specified in `docs/process/research-learning-flow.md`; implemented in `tests/unit/research-index-contract.test.js`). An overdue row alone does not authorize spending quota: the Orion schedules a light batch renewal by trigger source (the first one ran on 2026-11-18).
- Dates in this table were migrated on 2026-11-18 from the dates already in the index (no new research); **Confidence** is my classification of each existing note from its own evidence text, not a re-verification.

## Open GAPs (block a decision)

All three are from OPS-20 (#15). More web research is unlikely to close them: the notes report that no official or community statement was found. They need a **live Twitch test** on an affiliate test channel (already listed as a documented blocker in `test-research.md`), or an explicit owner rule that avoids depending on them.

1. **Pending UNFULFILLED redemptions:** whether Twitch expires or caps them in the request queue. This decides whether a non-eligible redemption may be left UNFULFILLED.
2. **Prime subscribers:** how Get Broadcaster Subscriptions represents Prime subs (official docs only partly confirm this). Partly closed by row 38: forum reports say Prime appears as ordinary tier 1000 and cannot be told apart; live confirmation is RT-A step A7. This decides whether Prime counts as eligible.
3. **Broadcaster in their own subscription list:** this is unknown for moderators/VIPs; row 38 found a 2020 Twitch-staff statement that the subscriptions API includes the broadcaster's own subscription. The current recommendation is to handle the broadcaster with an explicit rule.

Renewal of 2026-11-18 (row 15): the documentation questions are answered (`user_id` maximum 100, scope, `first`), so row 15 moved from GAP to REFRESH IF.
