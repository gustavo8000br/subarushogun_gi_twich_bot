# Runtime and boundaries
[Português brasileiro](../pt-BR/front-end-architecture/runtime-and-boundaries.md)


The approved OPS-15 direction is Next.js App Router with `output: 'export'`. Fastify remains the sole local runtime server and will serve the exported static panel and overlay assets on the existing same origin. No Next.js production server, public hosting, or production API proxy is introduced. `npm run dev` launches both Fastify (loopback, port 3109 by default) and Next, using a dev-only same-origin proxy to the explicitly validated loopback Fastify origin; that proxy is excluded from the static export. In Codespaces, the launcher passes Fastify the exact HTTPS origin for the forwarded Next port so local session and CSRF checks accept the browser's forwarded origin; other origins remain rejected, and production retains its localhost-only rule. On first run it copies `.env.product.example` to ignored `.env.product.local` without overwriting an existing file, then reads `DATABASE_URL`; with an empty URL the launcher provisions its isolated development database. This file is separate from AIOX's root `.env`. The command creates isolated TLS material under `.local/dev-tls`. The build-time Next/transpilation/bundling pipeline is the narrow exception to the previous no-framework/no-bundler constraint; application source remains JavaScript ESM with JSDoc, with no TypeScript adoption.

Use `trailingSlash: true` for production export: canonical panel paths such as `/queues/` map to `out/queues/index.html`, which `@fastify/static` serves with index handling. Development disables trailing-slash redirects so `/api/*` reaches Fastify without a 308. The `/overlay/` route exports to `out/overlay/index.html`; the build copies that document to the literal `out/overlay.html` alias without a redirect or rewrite. The Next foundation and its static assets are in the production image, while Fastify still serves the legacy `apps/web/` root until parity and cutover gates pass. Fastify must keep OAuth callback and all `/api/*`, `/health`, and `/overlay/api/*` routes explicitly registered before static serving. The bootstrap has separate panel and overlay route/layout/bundle entries; OBS must not load the panel bundle. The browser never imports Prisma or communicates with Twitch directly. The development API binds to loopback. If `DATABASE_URL` is empty, the launcher starts its separate development PostgreSQL service, snapshots before migrations, and leaves product Compose services and volumes untouched.

The exact overlay URL and authorization contract are an open architecture gate: OPS-13/#57 proposes a capability-free local projection addressed by widget ID, while existing OPS-13 criteria preserve the token capability flow. Resolve this conflict with `$aiox-architect` before migrating or cutting over the overlay. Keep #57 open until native OBS/CEF acceptance.

First-party TSV catalogs remain in the product image. Complete community catalogs live under host `.local/community-catalogs`, mounted into `/app/.local/community-catalogs` read-only with a distinct Compose bind; catalog discovery validates and merges both roots for panel, setup, chat and overlay. The overlay's current catalog cache has a five-second TTL. See [OPS-15](../stories/OPS-15/story.md) for the staged migration and evidence gates.

The local `GET /health` response may include nullable `last_reconciliation_at`, derived from the current Twitch integration process memory. It is not persisted and resets to null on API restart until the next completed reconciliation.

For host development, the API writes the product-locale bootstrap projection under `.local/dev/product-locale.state`; the launcher honors an explicitly configured `PRODUCT_LOCALE_PROJECTION_FILE`. This keeps the development projection in the worktree instead of using the container-only `/app/.local` default.
