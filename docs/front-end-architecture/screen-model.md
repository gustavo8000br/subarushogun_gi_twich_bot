# Screen model
[Português brasileiro](../pt-BR/front-end-architecture/screen-model.md)


Setup/reconnect → overview/health → queue list/detail and attendance → Twitch communication and viewer-points operations → account/settings/permissions/commands/locale → widget management. The OBS overlay is a separate capability-based presentation entry at `/overlay.html?ref=...#token`. Preserve each current screen/action and its applicable loading, empty, disconnected, stale, partial, error, success, pending, unknown and conflict states. Queue controls reflect current lifecycle while server validation remains authoritative. Destructive actions retain their existing review and confirmation steps. OPS-15's migration matrix records the existing endpoint, locale/catalog and tests for each action before legacy removal.

The initial Next overview loads `/api/state` for product version, persisted locale and connectivity, and `GET /api/queues` for operator queue counts. It must distinguish loading/API failure from a valid empty queue result. The Next queue list now renders this protected operator projection, separates waiting/called/in-service entries, localizes lifecycle/sync state and omits UID values. It distinguishes loading/API failure from a valid empty queue result. Queue lifecycle controls and detail editing remain migration work.

For the Twitch connection screen, preserve the existing sequence: validate/save the confidential app credentials, show the exact local callback URL, then authorize or reconnect the channel. Never redisplay a saved client secret. Present channel eligibility and chat/reward connectivity as separate textual statuses; keep connection and reconciliation actions tied to the existing setup/reconciliation API contracts. Return errors as localized safe feedback and do not infer connection success before a fresh setup read.

For the command permission editor, the default minimum role for configurable commands is **follower**. The streamer may change each configurable command's minimum role; that threshold applies to everyone invoking that command. Commands whose access is fixed to streamer/moderators remain locked and unchanged. Preserve the existing streamer override, inherited higher roles, VIP setting, and Twitch follower-scope authorization flow. Verify persisted results after reload; do not silently broaden the setting into a global threshold unless the existing backend contract provides one.

## Operations route — UX-approved before implementation

The existing `/operations/` route helps the streamer identify Twitch work that needs attention. Keep three semantic groups: **Twitch synchronization** (reward updates/deletions), **Channel Points refunds** (viewer refunds), and **redemption fulfillment** (Twitch confirmation that service was completed). A record shows its operation type, relevant redemption/reward identifier, textual status, attempt count, and only actions allowed by the existing API contract. Never present an unknown result as confirmed.

Support loading, valid empty, pending, processing, confirmed, unknown, failed, conflict, manually resolved, retry, and API error states. Preserve the existing global Twitch reconciliation, per-operation retry, manual-resolution and continue-deletion actions. Require localized confirmation before manual resolution or continuing a reward deletion; the dialog must explain manual resolution does not confirm Twitch and deletion may be irreversible. Do not trigger mutations in presentation tests.

Use titled sections, readable status text beyond color, accessible control names, predictable keyboard order and visible focus. At 390px, stack metadata/actions without horizontal page scrolling; at wider viewports keep operation details grouped and scannable. Use current shared panel heading/card/status/feedback/empty-state patterns. Keep all content equivalent in `pt-BR`, `en`, and `es`. This review approves the information hierarchy and interaction contract; mock data validates presentation only, not remote transitions or Twitch safety.
