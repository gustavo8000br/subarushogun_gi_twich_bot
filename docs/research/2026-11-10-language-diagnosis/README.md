## 4. Problems found

| ID | Class | Finding (evidence) | Impact |
|---|---|---|---|
| P-01 | Proven | `tsconfig.json` has `strict: false`; no `noImplicitAny`. 61 explicit `any` and many unannotated parameters pass the gate. | A wrong library property or error shape is not caught (the motive of OPS-24). |
| P-02 | Proven | `eslint.config.js` lints `tests/**/*.js` only. `tests/**/*.mjs` (29 files, 3,464 lines) and `tests/**/*.jsx` (22 files, 3,187 lines) match no config block, so ESLint skips them silently. Confirm with a planted violation before fixing. | About 6,650 lines of tests with no lint. |
| P-03 | Proven | `typecheck` includes `apps/**/*.{js,mjs}` only: `tests/**` (about 32,100 lines) and all `.jsx` (apps 3,289 lines) are not type-checked. `typecheck:frontend` covers only `apps/shared/panel/**/*.mjs` (13 files, 807 lines). | Fakes can diverge from real classes without failing the compiler. |
| P-04 | Proven | `pg` 8.23.1 ships no types and `@types/pg` is not installed (`import pg from 'pg'` is implicitly `any`). It passes only because `strict` is off. | Becomes error TS7016 when strict turns on; add `@types/pg` (research whether still correct for `pg` 8.23). |
| P-05 | Proven | No formatter anywhere. | Style drift; noisy diffs; the Biome formatting commit will touch everything. |
| P-06 | Proven | `actionlint -shellcheck=` disables ShellCheck for workflow `run:` blocks; no ShellCheck on `installer.sh` and `post-create.sh`; no PSScriptAnalyzer on `installer.ps1`/validator; no hadolint on the Dockerfile. | Shell-class defects (quoting, unset variables, portability) are found only by tests. |
| P-07 | Proven | `installer.ps1` sets `$ErrorActionPreference = 'Stop'` but not `Set-StrictMode`. | Typos in variable names evaluate to `$null` silently. |
| P-08 | Proven | `installer.sh` is `#!/bin/sh` with `set -eu` and no `pipefail`; it uses pipes such as `sed ... \| head`. | A failing left side of a pipe is hidden. Portable alternatives exist (check each pipe or use temp captures). |
| P-09 | Proven | Dockerfile: `npm ci` in the `dependencies` stage installs devDependencies (vitest, eslint, typescript, jsdom, playwright-core, prisma CLI) and the runtime stage copies that whole `node_modules`. | Larger image and attack surface. Prisma CLI is needed at runtime by `migrate`; the rest is not. Size is **to measure**. |
| P-10 | Proven | `compose.yaml`: only `bootstrap` has a restart value (`"no"`); `bot` and `db` have none (the dev stack uses `unless-stopped`). | A crashed bot or a reboot leaves the product down; confirm intent with `@devops` (the installer may restart explicitly). |
| P-11 | Opportunity | Compose hardening for `bot` and `migrate`: `read_only: true` + `tmpfs`, `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`, `mem_limit`, `pids_limit`. `bootstrap` runs as root (`0:0`) by design to write secrets. | Smaller blast radius. Needs real-run validation (Next writes cache, PostgreSQL volume). |
| P-12 | Opportunity | `actions/checkout` lacks `persist-credentials: false` in every job; no Dependabot/Renovate for action SHAs and npm. | Token stays in `.git/config` for later steps; pinned SHAs go stale. |
| P-13 | Opportunity | Floating `windows-latest` and `macos-15` against pinned `ubuntu-24.04`. Windows/macOS steps without `shell:` (installer-smoke "Package" and "Launch" steps) run under `pwsh` on Windows and `bash` elsewhere, with different quoting. | Runner image changes can break the Windows leg without a code change. |
| P-14 | Opportunity | `.opengrep/rules.yml` has 2 rules (HTML sink, credential logging), JavaScript only. | Coverage of Dockerfile/YAML/shell rules is untested. |
| P-15 | Opportunity | Images are pinned by tag (`node:24.20.0-alpine3.24`, `postgres:18.6-bookworm`), not digest. | Tag re-push is not detected; reproducibility vs. maintenance trade-off. |
| P-16 | Opportunity | `-ExecutionPolicy Bypass` in the generated `.bat` launcher. | Common for downloadable installers; document it and show the script hash in the release notes. |
| P-17 | To measure | Event Loop delay, RSS/heap, queue-repository query cost, bundle size of the Next panel and overlay, image size, Vitest transform time for `.ts`. | See section 7. |
| P-18 | To measure | Number of `strict` errors per folder (a read-only `tsc --strict` run by `@qa`; the OPS-24 risk 3 already requires it before each slice). | Sizes each TS slice. |
| P-19 | To measure | Vitest suite duration split by unit / integration (PostgreSQL + Compose) and CI wall time per job (35 min limit on the test job). | Decides where a faster runner or sharding pays. |

Positive findings worth keeping: 0 suppression comments, 1 `eslint-disable` (justified), pinned SHAs, least-privilege workflow permissions, non-root runtime user, healthchecks, explicit LF/CRLF policy.

### 5.2 Dependencies without types

None blocks the work. Twurple, Fastify, Next, React (`@types/react`), js-yaml and the generated Prisma client carry or generate types. Only `pg` has none (P-04). ### 5.4 Risks specific to this repository

- **Type stripping accepts only erasable syntax** and does no checking: `erasableSyntaxOnly` plus a mandatory `tsc` gate (a green `node` run proves nothing).
- **`.ts` specifiers in `apps/shared`**: Next/Turbopack and `allowImportingTsExtensions` behavior is not verified (To research); reason to leave `apps/shared` as `.mjs`.
- **Three silent-ignore surfaces** (Vitest `include`, ESLint/Biome globs, OpenGrep `languages`): the P-02 finding shows the same class already exists for tests today.
- **Strict flip** is the real cost: P-18 sizes it. Until measured, no slice should be promised a date.
- **Docker/installer**: the image copies `apps` as source and runs `node apps/infra/scripts/start-product.mjs`; type stripping keeps that model, but the packager and `compose` contract tests must be re-run per slice.
- **TypeScript 7.0.2 has no API**: `typescript-eslint` stays blocked; the research note lists the revisit triggers (issue #10940, Biome nursery promotion).

### 5.5 What not to migrate (preliminary)

`.jsx` UI and `apps/shared` (decided out of scope and coupled to the bundler); the 156 unit tests; `apps/infra` boot scripts; shell/PowerShell (a different tooling track, not TypeScript); Prisma schema; generated `.bat`. A first cheap step that gives most of the type safety without renaming anything: `strict` per folder on the existing `.mjs` files with JSDoc, plus tests under `checkJs`. Whether `.ts` then adds enough over strict JSDoc is **a decision to take with the measured error counts (P-18)**: the owner decided for `.ts`; this diagnosis only offers the cheaper intermediate step as an option, with its trade-off (no annotation syntax, verbose generics in JSDoc, weaker agent ergonomics).
