### 2.3 D-1 (parar/religar o PostgreSQL com a API no ar)

Com a API recém-iniciada e os widgets consultando, `docker stop qa-g1-db`: o processo da API continuou vivo, `/health` respondeu `status: unavailable` com `database: unavailable`, os widgets mostraram "Atualização atrasada" e mantiveram o valor; uma linha JSON segura foi registrada (`event: database_pool_error`, `level: error`, `source: api.database`, `errorCode: sqlstate_57P01`, `details.reason: idle_client_lost`; sem mensagem, host, stack nem connection string). Após `docker start`, `/health` voltou a `ok` / `database: connected` em até 8 s e os widgets saíram do estado atrasado sem reinício algum. Foram três paradas: as duas primeiras não registraram nada (nenhuma conexão ociosa naquele instante) e o processo sobreviveu; a terceira, após um início novo da API com conexões ociosas, registrou o evento acima. O código antigo caía com `Unhandled 'error' event` (`evidence/api-crash-on-db-stop.log` do relatório anterior). Mutações: o handler lança quando o logger falha -> `pool-error-handler.test.js` falha (1); handler nunca registrado (`pool.on('x-error')`) -> 3 testes falham, inclusive a integração com PostgreSQL real; o registro em `server.mjs` também é fixado por um teste de contrato de código-fonte (`pool-error-handler.test.js:40`). **D-1 corrigido.** Resíduo (recomendação, não defeito desta fatia): `compose.yaml:45`, serviço `bot`, continua sem política `restart:`; o `@dev` documentou isso como decisão do proprietário/produto.
