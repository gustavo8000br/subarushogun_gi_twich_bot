# Decisões de integração

[English](../integrations.md)

**Documentação consultada:** 2026-10-06 (UTC). Os formatos da API do SDK também foram conferidos nas versões instaladas neste repositório. OAuth, validação/renovação de token, elegibilidade Affiliate/Partner e disponibilidade da API Channel Points, ciclo de vida das recompensas gerenciadas, adapters Helix de resgate/chat/saúde, normalização EventSub WebSocket e reconciliação estão implementados e cobertos por testes. Em 2026-10-06, uma verificação real autorizada e somente de leitura retornou HTTP 200 em `/health`, com PostgreSQL conectado, canal autenticado identificado como inelegível e latência Helix de 193 ms (uma atualização posterior do painel mediu 322 ms). Não foram feitas alterações de recompensa, resgate, mensagem de chat nem operação EventSub; escritas Twitch reais continuam sem validação. Criar uma fila registra duravelmente a solicitação de recompensa Twitch pausada; criação ambígua pode ser resolvida no painel por ação auditada e revalidada. A FND-6 está concluída e foi mergeada na PR #22; ela oferece limites/cooldown nativos Twitch na criação e edição remota protegida/versionada por uma outbox durável. Testes PostgreSQL cobrem persistência, restrições, limpeza de privacidade e confirmação das alterações.

### Pesquisa do runtime de contêiner

A imagem da API usa a imagem oficial fixada `node:24.20.0-alpine3.24`. Em 2026-10-05, build Docker AMD64 limpo e inicialização Compose isolada real confirmaram que Prisma 6.19.3 gera e carrega sua engine `linux-musl-openssl-3.0.x` no Alpine 3.24. Bootstrap, as três migrations versionadas, runtime sem root, health HTTPS e conexão ao banco passaram. Depois, a stack Compose local normal foi reconstruída e reiniciada sobre os volumes existentes de PostgreSQL/segredos, sem apagá-los. PostgreSQL continua em `postgres:18.6-bookworm`. O GitHub Actions/QEMU pós-merge compilou e publicou as imagens AMD64 e ARM64, verificadas nos manifests GHCR `main` e `v0.1.0-3e0c935-alpha`. O uso em hosts Windows/macOS não foi repetido após esta troca de base.

Referências: [tags oficiais da imagem Node](https://hub.docker.com/_/node/tags?name=24.20.0-alpine), [guia de deploy Docker do Prisma](https://docs.prisma.io/docs/guides/deployment/docker), [engines de plataforma do Prisma ORM 6](https://docs.prisma.io/docs/orm/v6/reference/prisma-schema-reference).

## Mapa de operações Twitch

| Operação | Endpoint ou evento EventSub | Escopo/autorização necessária | Adaptação no SDK |
| --- | --- | --- | --- |
| Validar Client ID/Secret | `POST https://id.twitch.tv/oauth2/token` com `grant_type=client_credentials` | Client ID + Secret; app token | Implementado com `fetch` sanitizado no backend; token temporário é descartado. Não usar uma chamada Helix com token de usuário para validar o Secret. |
| Conectar o broadcaster | Authorization Code; callback `https://localhost:${APP_PORT:-3000}/callback`; validação via `GET https://id.twitch.tv/oauth2/validate` | `channel:manage:redemptions`, `user:read:chat`, `user:write:chat` | `createOAuthStateStore` e `RefreshingAuthProvider`; validação no início/por hora e persistência de renovação. `state` OAuth é único, curto e vinculado à sessão local inicial. |
| Ler elegibilidade do broadcaster | `GET /helix/users` | Token de usuário do broadcaster conectado | Implementado por `ApiClient.users.getUserById`; verificar `broadcasterType` antes de habilitar pontos do canal. |
| Medir tempo de resposta da API Twitch | `GET /helix/users?id=<broadcaster_id>` | Token de usuário do broadcaster autenticado; esta consulta não requer escopo adicional | `ApiClient.users.getUserById` é chamado para canais conectados e canais autenticados porém inelegíveis. `/health` preserva a elegibilidade enquanto informa a latência, mantém a medição em cache por 60 segundos e nunca expõe o perfil retornado. Canais inelegíveis mantêm a renovação do token para essa consulta somente de leitura, sem iniciar processamento de recompensas/chat EventSub. |
| Verificar disponibilidade de Channel Points e capacidade de recompensas | `GET /helix/channel_points/custom_rewards` | Token do usuário com `channel:manage:redemptions`; ID do broadcaster deve corresponder ao token | Consultar por `ApiClient.channelPoints.getCustomRewards(broadcasterId, false)` somente após validar Affiliate/Partner. Contar todas as recompensas, inclusive criadas por outros apps e desativadas; alertar a partir de 45 e impedir criação quando o total observado for 50. Falha da API mantém a integração indisponível sem expor detalhes do SDK. |
| Gerenciar recompensas criadas pelo app | `POST`, `PATCH`, `DELETE /helix/channel_points/custom_rewards` | `channel:manage:redemptions`; broadcaster e propriedade do app devem corresponder | Workers duráveis criam, editam, abrem/fecham, arquivam e excluem recompensas gerenciadas pelo ID criado pelo app. Criação e edição usam limites por live/por pessoa e cooldown global da Twitch; edições guardam snapshot anterior, verificam propriedade/configuração antes do PATCH e consultam novamente após resposta perdida. A exclusão pagina todos os resgates não cumpridos e aguarda cancelamentos confirmados antes do DELETE Twitch. A Twitch limita um canal a 50 recompensas (incluindo desativadas); título até 45 e prompt até 200 caracteres. |
| Observar resgates | `channel.channel_points_custom_reward_redemption.add` e `.update` | `channel:manage:redemptions` para o broadcaster conectado | `EventSubWsListener.onChannelRedemptionAdd` / `onChannelRedemptionUpdate`; normalizar os valores do SDK para estados internos e deduplicar pelo ID do resgate. Uma queda abrupta no WebSocket não reproduz os eventos perdidos; é preciso reconciliar com Helix. |
| Reconciliar recompensas pendentes | `GET /helix/channel_points/custom_rewards/redemptions` (paginar `UNFULFILLED`) | `channel:manage:redemptions`; recompensa criada por esta aplicação | `ApiClient.channelPoints.getRedemptionsForBroadcasterPaginated`; consumir todas as páginas e considerar uma falha parcial como reconciliação incompleta. |
| Cancelar ou concluir resgate | `PATCH /helix/channel_points/custom_rewards/redemptions` | `channel:manage:redemptions`; somente o app criador pode gerenciar | `ApiClient.channelPoints.updateRedemptionStatusByIds`; interpretar `CANCELED` como reembolso e `FULFILLED` como consumo somente após confirmar o resultado. Consultar estado remoto após resposta incerta. |
| Receber comandos do chat | `channel.chat.message` | `user:read:chat` para o usuário autorizado do streamer | `EventSubWsListener.onChannelChatMessage`; usar identidade e badges confiáveis do evento e ignorar comandos de outros canais no Shared Chat. |
| Consultar/editar catálogo de cargos dos comandos | `GET /api/command-catalog`, `PATCH /api/command-policies` locais; `!queue comandos` e `!<fila> comandos` no chat | Sessão/CSRF do painel local; cargos Twitch vêm dos badges atuais, sem escopo adicional | Registro canônico alimenta parser, autorização, ajuda e painel. Políticas usam listas explícitas com semântica OU, persistidas/auditadas no PostgreSQL; `queue` fica reservado. `!queue ping` global exige streamer/moderador e usa o probe `/health` em cache, sem chamada Helix disparada pelo chat. |
| Enviar resposta no chat | `POST /helix/chat/messages` | `user:write:chat` | `ApiClient.chat.sendChatMessage`; conferir `is_sent` e motivo de descarte. Sucesso HTTP, sozinho, não confirma entrega. A Twitch limita cada mensagem a 500 caracteres. |

As requisições de recompensa devem usar `should_redemptions_skip_request_queue=false`; os campos recebidos de API/EventSub/SDK devem ser normalizados no limite do adaptador. A Twitch é a fonte da verdade dos pontos. Somente o aplicativo que criou a recompensa pode gerenciar seus resgates. Apagar uma recompensa com resgates pendentes pode concluí-los, portanto a exclusão deve esperar a confirmação remota dos cancelamentos.

Este produto usa EventSub WebSocket e Helix Send Chat Message com a conta do streamer. Não usa IRC nem uma segunda conta de bot. Mensagens com token de usuário podem ser propagadas pelo Shared Chat; o produto não deve prometer o contrário.

## Achados adicionais da pesquisa Twitch de 2026-10-06

| Capacidade | Contrato oficial | Consequência para o produto |
| --- | --- | --- |
| Limites nativos da recompensa da fila | O create/update de Custom Reward na Helix expõe `max_per_stream_setting`, `max_per_user_per_stream_setting` e `global_cooldown_setting`; o canal pode ter até 50 rewards, incluindo desativadas; título único de até 45 caracteres; descrição de até 200. | A FND-6 persiste valores positivos opcionais no PostgreSQL (null desativa a configuração) e envia-os na criação/edição da recompensa do app. A edição continua pendente até o worker confirmar o mesmo ID de recompensa e os valores solicitados. Não há contadores paralelos. |
| Propriedade e histórico das recompensas | Somente o app criador consulta resgates e altera/exclui sua recompensa. Registros cancelados/concluídos ficam disponíveis por apenas alguns dias. Excluir recompensa com resgates não cumpridos pode marcá-los como cumpridos. | Preservar recompensas dedicadas por fila, IDs estáveis, recuperação pela outbox durável e tratamento explícito de estado desconhecido; nunca adotar recompensa preexistente pelo título. |
| Chat e Pontos do Canal | `channel.chat.message` exige `user:read:chat`; EventSub de resgate exige `channel:read:redemptions` ou `channel:manage:redemptions`; mutações exigem `channel:manage:redemptions`. O contrato da assinatura de chat não declara exigência Afiliado/Parceiro, enquanto as operações Custom Reward declaram. | A FND-9 deve modelar chat e Pontos do Canal como capacidades separadas. A arquitetura é sustentada pela documentação, mas não comprova em tempo real chat em canal inelegível; verificar escopos OAuth e assinatura Twurple antes de implementar/afirmar. |
| Evidência de cargo para comandos | Mensagens chat EventSub incluem `badges` atuais, com exemplos de moderador/assinante. `GET /helix/channels/followers` com `user_id` específico exige `moderator:read:followers`; `channel.follow` emite somente eventos de follow. | A issue #17 pode usar badges da mensagem atual para cargos suportados. Não oferecer acesso por follower sem aprovação explícita do escopo adicional e comportamento para dados ausentes/antigos. Não persistir cargo inferido de mensagem antiga. |
| Limites API e resultado de mensagens | Retry HTTP 429 usa o horário do cabeçalho `Ratelimit-Reset`; Send Chat Message da Helix retorna `is_sent` e `drop_reason`, não apenas status HTTP. | Workers de pontos/recompensa devem respeitar cabeçalhos de reset; notificação de chat só conta como enviada após confirmação no resultado do SDK/API. |

## Contratos da infraestrutura local

## Integração OBS Browser Source da FND-7 — evidências e limites de aceite

| Operação | Endpoint/evento | Escopo | Decisão de adaptação |
| --- | --- | --- | --- |
| Renderizar um widget local | URL HTTPS local do app no OBS Browser Source (CEF) | Nenhum escopo Twitch; Page Permissions do OBS = None | Projeção somente de leitura, limitada ao widget e servida por HTTPS local; sem bindings/API de controle do OBS ou assets remotos. A confiança da CA nativa deve ser verificada nas versões exatas de SO/OBS/CEF antes de declarar suporte. Nunca usar HTTP nem desabilitar validação do certificado. |
| Atualizar dados do widget | Polling da projeção local same-origin a cada segundo | Nenhum | Medir a meta de dois segundos com oito páginas ativas/habilitadas; página descarregada enquanto oculta busca o estado atual ao voltar. O estado aberta/fechada só é projetado após confirmação da sincronização remota; estados pendentes, desconhecidos, com falha ou divergentes usam o fallback configurado. |
| Gerenciar um widget | `POST/PATCH/DELETE /api/overlay-widgets` e rotas de ciclo de capability | Sessão local do painel + CSRF + chave de idempotência existentes | Modelo/migration PostgreSQL, política de fontes/estilos permitidos, persistência somente SHA-256 da capability, URL HTTPS com fragmento emitida uma vez e projeção somente leitura via `Authorization` foram implementados; conferir evidências atuais da story antes de declarar FND-7 concluída. |

O escopo das fontes é explícito: nome/estado/quantidade aguardando da fila exigem `queue_id`; rótulo da conta e a pessoa chamada/em atendimento mais antiga globalmente são fontes do canal; texto fixo não tem fila. A posição da pessoa chamada vem do snapshot `previousPosition` persistido na auditoria. A projeção retorna somente `sourceType`, `value` selecionado, `fallbackText` e estilo; não inclui IDs de widget/fila, UID, hash do token ou outros registros de negócio. Leituras de capability mantêm um bloqueio PostgreSQL compartilhado durante a projeção; a exclusão aguarda uma leitura em andamento e nenhuma leitura termina depois do commit da exclusão. Respostas com URL de uso único não são armazenadas no replay de idempotência.

Verificação nativa (2026-10-06): Ubuntu 24.04, OBS Studio 32.2.2 (Flathub), `obs-browser` 2.26.9 / CEF 127.0.6533.120. A Browser Source inicialmente rejeitou a CA do app (`net::ERR_CERT_AUTHORITY_INVALID`); após importar a CA do app em um perfil NSS temporário do CEF, carregou por TLS 1.3 com estado de segurança `secure` e HTTP 200. Não houve bypass de certificado nem fallback HTTP. `webpage_control_level=0` foi lido de volta do OBS (Page Permissions=None). Oito fontes ativas simultâneas renderizaram dez rodadas de atualização no banco (80 medições commit→DOM); o máximo foi 905 ms, abaixo da meta de 2.000 ms. A execução autenticada final também verificou parada/reinício do bot, recuperação do valor stale, descarregamento/recarga da Browser Source e rotação de capability. A confiança temporária foi removida depois. OBS Studio 32.2.2 está instalado e disponível para o usuário. Esta evidência vale somente para essas versões Ubuntu/OBS/CEF; Windows e macOS não foram testados.

Após confiar no certificado local atual, a aceitação no Chrome cobriu criar/editar widget, copiar com sucesso o link de uso único, confirmar regeneração/revogação, excluir e selecionar uma fonte de fila apoiada por uma fixture descartável do PostgreSQL local. Fixture/widget foram removidos depois; a sincronização Twitch não foi exercitada. Todas as capabilities geradas foram invalidadas e, após atualizar, o painel ficou vazio. Há cobertura unitária/API. O harness está em `tests/e2e/overlay-browser.mjs`, exposto como `npm run test:e2e:overlay`; rode somente com Compose local isolado, as Browser Sources OBS descritas e a CA do app confiada pelo CEF.

| Tema | Contrato |
| --- | --- |
| Conexão ao banco | PostgreSQL é acessado pelo nome do serviço Compose `db`, nunca pelo `localhost` do contêiner; a connection string de runtime é montada com o segredo e nunca registrada em log. |
| Inicialização das migrations | `migrate` aguarda `db` saudável; `bot` aguarda a conclusão bem-sucedida das migrations. |
| Saúde | `/health` verifica PostgreSQL e retorna versão do produto, estado da integração Twitch e `twitch_api_ping_ms`; canais autenticados, inclusive inelegíveis, usam `GET /helix/users?id=<broadcaster_id>` da Helix em cache por 60 segundos. Sem credenciais, informa `not_configured` e não causa ciclo infinito de reinicialização. |
| Transporte do painel e OAuth | HTTPS em `https://localhost:${APP_PORT:-3000}`. O bootstrap persiste uma autoridade certificadora local e um certificado de servidor localhost no volume de segredos, exporta somente o certificado público da autoridade em `.local/` e monta a chave de servidor somente para leitura no serviço `bot`. O operador importa a autoridade certificadora no repositório confiável do usuário atual; não é necessário domínio público nem proxy. |

Revisão dos comandos de confiança por sistema (2026-10-06): Linux usa GNU `install -D` para criar o diretório destino e instalar a CA pública com modo 0644; as aspas em `"$PWD/.local/localhost-ca.crt"` permitem caminhos com espaços. Windows usa PowerShell `Import-Certificate` com `Cert:\CurrentUser\Root`; `Resolve-Path` expande o caminho relativo do projeto para um caminho absoluto. macOS usa `security add-trusted-cert -r trustRoot -k ~/Library/Keychains/login.keychain-db "$PWD/.local/localhost-ca.crt"`; omita `-d`, que seleciona as configurações administrativas de confiança, em vez das configurações padrão do usuário. A sintaxe foi conferida na documentação do [GNU Coreutils](https://www.gnu.org/software/coreutils/manual/html_node/install-invocation.html), [Import-Certificate da Microsoft](https://learn.microsoft.com/en-us/powershell/module/pki/import-certificate), [guia Apple do Acesso às Chaves](https://support.apple.com/guide/keychain-access/kyca2431/mac) e no [manual `security(1)` do macOS](https://manp.gs/mac/1/security). O projeto não executou a importação nativa no Windows/macOS nem validou confiança OBS nessas plataformas; há evidência somente do comportamento de cópia Linux e do relato do operador sobre o comando de trust store no Ubuntu.
| Encerramento e dados | SIGTERM/SIGINT fecha trabalho HTTP/banco; volumes nomeados do Compose preservam banco e segredo gerado. Instruções normais de parada nunca removem volumes. |
| ORM / transações | Prisma 6.19.3 usa `PrismaPg({ connectionString })` com `PrismaClient({ adapter })`. Transações interativas são curtas; um advisory lock transacional do PostgreSQL serializa mutações da fila, enquanto índices unique do banco continuam sendo a última proteção de concorrência. Nenhum I/O de rede acontece dentro de transações. |
| Migrations e testes ORM | Migrations Prisma são versionadas e executadas por `prisma migrate deploy`; contratos de teste usam PostgreSQL real e essas migrations, não SQLite nem Prisma mockado. |
| Registry de imagens | `ghcr.io/gustavo8000br/subarushogun_gi_twich_bot` | O pacote foi verificado como privado em 2026-10-07 por um pull anônimo que retornou HTTP 403. Enquanto estiver privado, use PAT clássico com `read:packages` de uma conta autorizada; quando a visibilidade do pacote for pública, pulls não exigem credenciais do registry. As visibilidades do repositório e do pacote são separadas. O produto nunca armazena tokens. |

Os documentos OAuth da Twitch ainda mostram `http://localhost:3000` nos exemplos ([guia OAuth](https://dev.twitch.tv/docs/authentication/getting-tokens-oauth/), [Get Started](https://dev.twitch.tv/docs/api/get-started/)). Durante esta instalação, o console de desenvolvedor recusou o valor configurado `http://localhost:3000/callback` e exigiu HTTPS. Por isso, o produto usa `https://localhost:3000/callback` por padrão e documenta a confiança na autoridade certificadora local. O `redirect_uri` OAuth permanece idêntico byte a byte entre o cadastro do app Twitch, o pedido de autorização, a troca do token e a exibição no painel.
