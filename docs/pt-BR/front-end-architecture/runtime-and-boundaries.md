# Runtime e limites
[English](../../front-end-architecture/runtime-and-boundaries.md)


A direção aprovada na OPS-15 é Next.js App Router com `output: 'export'`. Fastify continua como único servidor local de runtime e servirá os assets estáticos exportados do painel e do overlay na mesma origem existente. Não se adiciona servidor Next.js de produção, hospedagem pública ou proxy de API em produção. `npm run dev` inicia Fastify (loopback, porta 3109 por padrão) e Next, usando um proxy same-origin somente em desenvolvimento para a origem loopback Fastify validada explicitamente; esse proxy não entra na exportação estática. No Codespaces, o launcher informa ao Fastify a origem HTTPS exata da porta encaminhada do Next para que as verificações de sessão local e CSRF aceitem a origem encaminhada pelo navegador; outras origens continuam bloqueadas e produção mantém a regra localhost-only. Na primeira execução, copia `.env.product.example` para `.env.product.local`, ignorado pelo Git, sem sobrescrever arquivo existente, e então lê `DATABASE_URL`; se estiver vazia, o launcher provisiona seu PostgreSQL isolado de desenvolvimento. Esse arquivo é separado do `.env` raiz do AIOX. O comando cria certificados TLS isolados em `.local/dev-tls`. O pipeline de build/transpilation/bundling do Next é a exceção restrita à regra anterior sem framework/bundler; o código da aplicação permanece em JavaScript ESM com JSDoc, sem adoção de TypeScript.

Usar `trailingSlash: true` na exportação de produção: caminhos canônicos do painel, como `/queues/`, mapeiam para `out/queues/index.html`, servido pelo `@fastify/static` com tratamento de index. O desenvolvimento desativa redirects de barra final para que `/api/*` chegue ao Fastify sem 308. A rota `/overlay/` exporta para `out/overlay/index.html`; o build copia esse documento para o alias literal `out/overlay.html` sem redirect ou rewrite. A fundação Next e seus assets estáticos estão na imagem de produção, mas Fastify ainda serve a raiz legada `apps/web/` até a paridade e os gates de cutover. As rotas de callback OAuth, `/api/*`, `/health` e `/overlay/api/*` devem continuar explicitamente registradas no Fastify antes do serving estático. O bootstrap possui rotas/layouts/bundles separados para painel e overlay; OBS não pode carregar o bundle do painel. O navegador nunca importa Prisma nem acessa Twitch diretamente. A API de desenvolvimento usa bind loopback. Se `DATABASE_URL` estiver vazia, o launcher inicia seu PostgreSQL de desenvolvimento separado, cria snapshot antes das migrations e não altera serviços nem volumes Compose do produto.

A URL exata e o contrato de autorização do overlay estão em gate arquitetural: OPS-13/#57 propõe uma projeção local sem capability endereçada por widget ID, enquanto os critérios OPS-13 existentes preservam o fluxo de token capability. Resolver o conflito com `$aiox-architect` antes de migrar ou fazer cutover do overlay. Manter #57 aberta até o aceite OBS/CEF nativo.

Catálogos TSV first-party permanecem na imagem do produto. Catálogos comunitários completos ficam em `.local/community-catalogs` no host, montados como bind distinto somente leitura em `/app/.local/community-catalogs`; a descoberta valida e combina as duas raízes para painel, setup, chat e overlay. O cache atual de catálogos do overlay tem TTL de cinco segundos. Consulte a [OPS-15](../../stories/OPS-15/story.md) para a migração em fases e os gates de evidência.

A resposta local de `GET /health` pode incluir `last_reconciliation_at` anulável, derivado da memória do processo atual da integração Twitch. Não é persistido e volta a nulo ao reiniciar a API até a próxima conciliação concluída.

No desenvolvimento no host, a API grava a projeção de bootstrap do locale do produto em `.local/dev/product-locale.state`; o launcher respeita `PRODUCT_LOCALE_PROJECTION_FILE` configurado explicitamente. Assim, a projeção dev fica na worktree em vez de usar o caminho `/app/.local`, válido somente no container.
