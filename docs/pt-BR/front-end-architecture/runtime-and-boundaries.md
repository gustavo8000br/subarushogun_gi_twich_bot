# Runtime e limites
[English](../../front-end-architecture/runtime-and-boundaries.md)


A OPS-15 substituiu o plano anterior de export estático (histórico) por um runtime de dois processos. Em produção, a aplicação Next.js App Router em `apps/frontend/` roda no servidor Node do Next.js via HTTPS local na `PANEL_PORT` (3000 no contêiner, publicada somente como `127.0.0.1:${APP_PORT:-3000}`), e o Fastify roda como processo separado na `API_PORT` 3109 em loopback; `apps/infra/scripts/start-product.mjs` supervisiona os dois. Não há export estático, hospedagem pública nem nova porta pública. `npm run dev` inicia Fastify (loopback, porta 3109 por padrão) e Next, usando um proxy same-origin somente em desenvolvimento para a origem loopback Fastify validada explicitamente; esse proxy existe somente em desenvolvimento. No Codespaces, o launcher informa ao Fastify a origem HTTPS exata da porta encaminhada do Next para que as verificações de sessão local e CSRF aceitem a origem encaminhada pelo navegador; outras origens continuam bloqueadas e produção mantém a regra localhost-only. Na primeira execução, copia `.env.product.example` para `.env.product.local`, ignorado pelo Git, sem sobrescrever arquivo existente, e então lê `DATABASE_URL`; se estiver vazia, o launcher provisiona seu PostgreSQL isolado de desenvolvimento. Esse arquivo é separado do `.env` raiz do AIOX. O comando cria certificados TLS isolados em `.local/dev-tls`. O pipeline de build/transpilation/bundling do Next é a exceção restrita à regra anterior sem framework/bundler; o código da aplicação permanece em JavaScript ESM com JSDoc, sem adoção de TypeScript.

A produção usa `trailingSlash: false`. Os rewrites de produção do Next enviam `/api/*`, `/overlay/api/*`, `/health` e `/callback` para `FASTIFY_INTERNAL_ORIGIN` (padrão `https://localhost:3109`), que precisa usar HTTPS em host loopback com porta explícita. O Fastify aceita Host loopback na porta pública ou na `API_PORT` (`backendPort`), aceita somente Origin HTTPS loopback na porta pública e depois aplica as verificações de sessão e CSRF. O overlay OBS é servido diretamente pela rota Next `/overlay`, e o gerador do link do widget emite `/overlay?ref=...#token`, com a capability só no fragmento (`apps/api/src/domain/overlay-widget-service.mjs:41`). Desde a Onda 3 do cutover da OPS-15 ([registro](../stories/OPS-15/cutover-wave-3.md)), o alias legado `/overlay.html` e os arquivos do overlay vanilla não existem mais: nenhuma regra de desenvolvimento ou de produção reescreve `/overlay.html` (`apps/frontend/scripts/dev-proxy-config.mjs:19-28,39-48`, com `afterFiles` vazio), e `/overlay.html`, `/overlay.js` e `/overlay.css` recebem 404 do Next, sem redirecionamento (`tests/integration/compose-runtime.test.js:376`). Uma fonte do OBS ainda configurada com um link antigo `/overlay.html` precisa de um link novo gerado. Desde a Onda 1 do cutover da OPS-15 (2026-10-27, [registro](../stories/OPS-15/cutover-wave-1.md)), a `/` de produção é a Visão geral do painel Next (`apps/frontend/app/(panel)/page.jsx:8`) e o Fastify não serve nenhum arquivo de navegador: os únicos rewrites de produção para o Fastify são `/api/*`, `/overlay/api/*`, `/health` e `/callback` (`apps/frontend/scripts/dev-proxy-config.mjs:41-46`), `apps/api/src/server.mjs` não registra rota estática, e `/app.js`, `/styles.css`, `/index.html` e `/shared/panel/*` recebem 404 do Next (`tests/integration/compose-runtime.test.js:372`). Os arquivos restantes de `apps/web/` (painel vanilla e catálogos de localização) continuam no disco, mas não são servidos; os catálogos saem na Onda 2 do cutover e o painel vanilla é removido na Onda 4. `legacy` é somente referência histórica, nunca fallback nem alvo de rollback. Painel e overlay têm entradas separadas de rota/layout/bundle; o OBS não pode carregar o bundle do painel. O navegador nunca importa Prisma nem acessa Twitch diretamente. A API de desenvolvimento usa bind loopback. Se `DATABASE_URL` estiver vazia, o launcher inicia seu PostgreSQL de desenvolvimento separado, cria snapshot antes das migrations e não altera serviços nem volumes Compose do produto.

A URL exata e o contrato de autorização do overlay estão em gate arquitetural: OPS-13/#57 propõe uma projeção local sem capability endereçada por widget ID, enquanto os critérios OPS-13 existentes preservam o fluxo de token capability. Resolver o conflito com `$aiox-architect` antes de migrar ou fazer cutover do overlay. Manter #57 aberta até o aceite OBS/CEF nativo.

Catálogos TSV first-party permanecem na imagem do produto. Catálogos comunitários completos ficam em `.local/community-catalogs` no host, montados como bind distinto somente leitura em `/app/.local/community-catalogs`; a descoberta valida e combina as duas raízes para painel, setup, chat e overlay. O cache atual de catálogos do overlay tem TTL de cinco segundos. Consulte a [OPS-15](../../stories/OPS-15/story.md) para a migração em fases e os gates de evidência.

A resposta local de `GET /health` pode incluir `last_reconciliation_at` anulável, derivado da memória do processo atual da integração Twitch. Não é persistido e volta a nulo ao reiniciar a API até a próxima conciliação concluída.

No desenvolvimento no host, a API grava a projeção de bootstrap do locale do produto em `.local/dev/product-locale.state`; o launcher respeita `PRODUCT_LOCALE_PROJECTION_FILE` configurado explicitamente. Assim, a projeção dev fica na worktree em vez de usar o caminho `/app/.local`, válido somente no container.
