# Integration decisions

[Português brasileiro](pt-BR/integrations.md)

**Documentation checked:** 2026-10-06 (UTC). SDK API shapes were also checked against the versions installed in this repository. OAuth, token validation/refresh, Affiliate/Partner and Channel Points API eligibility probing, managed reward lifecycle, Helix redemption/chat/health adapters, EventSub WebSocket normalization and reconciliation are implemented and covered by tests. An operator-authorized, read-only live smoke check on 2026-10-06 returned HTTP 200 from `/health`, with PostgreSQL connected, the authenticated channel reported ineligible, and Twitch Helix latency measured at 193 ms (a later panel refresh measured 322 ms). No reward mutation, redemption change, chat message, or EventSub operation was performed; live Twitch write behavior remains unverified. Queue creation durably requests a paused Twitch reward; ambiguous creation can be resolved through an audited, revalidated panel action. FND-6 is complete and merged in PR #22; it supports Twitch-native redemption caps and cooldown on creation, plus protected, version-checked remote reward edits through a durable outbox. PostgreSQL integration tests cover persistence, constraints, privacy clearing, and update confirmation.

### Container runtime research

The API image is pinned to the official `node:24.20.0-alpine3.24` image. On 2026-10-05, a clean AMD64 Docker build and a real isolated Compose startup confirmed Prisma 6.19.3 generates and loads its `linux-musl-openssl-3.0.x` engine on Alpine 3.24. Bootstrap, the three versioned migrations, non-root runtime, HTTPS health endpoint and database connection passed. The regular local Compose stack was then clean-built and restarted on the existing PostgreSQL/secrets volumes without deleting them. PostgreSQL remains `postgres:18.6-bookworm`. Post-merge GitHub Actions/QEMU built and published both AMD64 and ARM64 images, verified in the GHCR `main` and `v0.1.0-3e0c935-alpha` manifests. Windows/macOS host runs have not been repeated after this base change. FND-5 and FND-6 are complete and merged in PRs #16 and #22; live Twitch reward writes remain unverified.

References: [official Node image tags](https://hub.docker.com/_/node/tags?name=24.20.0-alpine), [Prisma Docker deployment guide](https://docs.prisma.io/docs/guides/deployment/docker), [Prisma ORM 6 platform engines](https://docs.prisma.io/docs/orm/v6/reference/prisma-schema-reference).

## Twitch operation map

| Operation | Endpoint or EventSub event | Required scope/auth | SDK adaptation |
| --- | --- | --- | --- |
| Validate Client ID/Secret | `POST https://id.twitch.tv/oauth2/token` with `grant_type=client_credentials` | Client ID + Secret; app token | Implemented with a sanitized backend `fetch`; temporary app token is discarded. Do not use a user-token Helix call to validate the secret. |
| Connect the broadcaster | Authorization Code flow; callback `https://localhost:${APP_PORT:-3000}/callback`; token validation via `GET https://id.twitch.tv/oauth2/validate` | `channel:manage:redemptions`, `user:read:chat`, `user:write:chat` | `createOAuthStateStore` plus `RefreshingAuthProvider`; startup/hourly token validation and refresh persistence. OAuth `state` is one-time, short-lived, and bound to the initiating local session. |
| Read broadcaster eligibility | `GET /helix/users` | User token for the connected broadcaster | Implemented through `ApiClient.users.getUserById`; inspect `broadcasterType` before enabling channel points. |
| Measure Twitch API response time | `GET /helix/users?id=<broadcaster_id>` | Authenticated broadcaster's user token; no additional scope for this lookup | `ApiClient.users.getUserById` runs for connected channels and authenticated but ineligible channels. `/health` preserves eligibility status while reporting latency, caches the measurement for 60 seconds, and never exposes the returned profile. Ineligible channels retain token refresh for this read-only probe but do not start reward/chat EventSub processing. |
| Verify Channel Points availability and reward capacity | `GET /helix/channel_points/custom_rewards` | User token with `channel:manage:redemptions`; broadcaster ID must match the token | Probe through `ApiClient.channelPoints.getCustomRewards(broadcasterId, false)` only after Affiliate/Partner eligibility. Count all rewards, including those created by other apps and disabled rewards; warn at 45 and prevent create when the observed count is 50. An API failure keeps the integration unavailable without exposing SDK details. |
| Manage app-owned rewards | `POST`, `PATCH`, `DELETE /helix/channel_points/custom_rewards` | `channel:manage:redemptions`; broadcaster and app ownership must match | Durable workers create, edit, open/close, archive and delete managed rewards by the app-created reward ID. Creation and edits use Twitch-native per-stream/per-user limits and global cooldown; edits preserve a prior-state snapshot, verify ownership/configuration before PATCH, and reconcile a lost response before retry. Deletion paginates all unfulfilled redemptions and waits for confirmed cancellation before Twitch DELETE. Twitch currently limits a channel to 50 rewards (including disabled rewards); title max 45 and prompt max 200 characters. |
| Observe reward redemptions | `channel.channel_points_custom_reward_redemption.add` and `.update` | `channel:manage:redemptions` for the connected broadcaster | `EventSubWsListener.onChannelRedemptionAdd` / `onChannelRedemptionUpdate`; normalize SDK values to internal states and deduplicate by redemption ID. WebSocket reconnect does not replay an abrupt gap; reconcile with Helix. |
| Reconcile pending rewards | `GET /helix/channel_points/custom_rewards/redemptions` (paginate `UNFULFILLED`) | `channel:manage:redemptions`; reward must belong to this app | `ApiClient.channelPoints.getRedemptionsForBroadcasterPaginated`; consume all pages and treat partial failures as incomplete reconciliation. |
| Cancel or fulfill a redemption | `PATCH /helix/channel_points/custom_rewards/redemptions` | `channel:manage:redemptions`; only the creating application may manage it | `ApiClient.channelPoints.updateRedemptionStatusByIds`; map `CANCELED` to refund and `FULFILLED` to point consumption only after a confirmed result. Query remote state after uncertain responses. |
| Receive chat commands | `channel.chat.message` | `user:read:chat` for the streamer's authorized user | `EventSubWsListener.onChannelChatMessage`; use trusted event identity and badges, ignore commands from other channels in Shared Chat. |
| Show/edit command role catalog | Local `GET /api/command-catalog`, `PATCH /api/command-policies`; chat `!queue comandos` and `!<queue> comandos` | Existing local panel session/CSRF; Twitch roles come from current chat badges, no additional scope | Canonical command registry feeds parser, authorization, chat help, and the panel. Policies are explicit OR allowlists persisted/audited in PostgreSQL; `queue` is reserved. Global `!queue ping` is streamer/moderator-only and reads the cached `/health` probe, not a chat-triggered Helix request. |
| Send chat response | `POST /helix/chat/messages` | `user:write:chat` | `ApiClient.chat.sendChatMessage`; inspect the response's `is_sent` and drop reason. HTTP success alone is not delivery confirmation. Twitch caps a message at 500 characters. |

The reward requests must use `should_redemptions_skip_request_queue=false`, and incoming API/EventSub/SDK fields must be normalized at the adapter boundary. Twitch is authoritative for point status. Only the application that created a reward can manage its redemptions. Deleting a reward while redemptions are pending may fulfill them, so deletion must wait until cancellation is remotely confirmed.

This product uses EventSub WebSocket and Helix Send Chat Message with the streamer's account. It does not use IRC or a second bot account. Shared Chat may propagate user-token messages; the product must not promise otherwise.

## Additional Twitch findings from the 2026-10-06 story audit

| Capability | Official contract | Product consequence |
| --- | --- | --- |
| Native queue-reward limits | Helix Custom Reward create/update exposes `max_per_stream_setting`, `max_per_user_per_stream_setting`, and `global_cooldown_setting`; a channel can have up to 50 rewards including disabled rewards; title is unique and at most 45 characters; prompt at most 200. | FND-6 now stores optional positive values (null disables each setting), persists them on PostgreSQL and sends them on app-owned reward create/update. Remote edits remain pending until the worker confirms the same reward ID and requested values. No shadow counters are maintained. |
| Reward ownership and history | Only the creating app can retrieve that reward's redemptions and mutate/delete it. Canceled/fulfilled records are available for only a few days. Deleting with unfulfilled redemptions may mark them fulfilled. | Preserve dedicated per-queue rewards, stable reward IDs, durable outbox recovery, and explicit unknown-state handling; never adopt a pre-existing reward by title. |
| Chat vs Channel Points | `channel.chat.message` requires `user:read:chat`; custom reward redemption EventSub requires `channel:read:redemptions` or `channel:manage:redemptions`; mutations require `channel:manage:redemptions`. The chat subscription contract does not state an Affiliate/Partner requirement, while Custom Reward endpoints do. | FND-9 should model chat and Channel Points as separate capabilities. This is documentation-supported architecture, not live proof of chat operation for an ineligible channel; verify OAuth scopes and Twurple subscription behavior before implementation/claim. |
| Role evidence for command permissions | Chat EventSub messages carry current `badges`, including moderator/subscriber examples. `GET /helix/channels/followers` with a specific `user_id` requires `moderator:read:followers`; `channel.follow` only emits follow events. | Issue #17 can use current-event badges for supported roles. Do not offer follower gating without explicit product approval of the additional scope and stale/missing-data behavior. Do not persist a role inferred from an old message. |
| API rate limits and message outcomes | HTTP 429 retry timing uses `Ratelimit-Reset`; Helix Send Chat Message returns `is_sent` and `drop_reason`, not just HTTP status. | Financial/reward workers must respect Twitch reset headers; chat notifications only count as delivered when the SDK/API result confirms send. |

The full story-by-story comparison and planning recommendations are recorded in the [Twitch capability gap audit](stories/TWITCH-CAPABILITY-GAP-ANALYSIS.md) and its [pt-BR translation](pt-BR/stories/TWITCH-CAPABILITY-GAP-ANALYSIS.md). No code behavior or story completion is asserted by this documentation update.

## Local infrastructure contracts

## FND-7 OBS Browser Source integration — implementation evidence and acceptance limits

| Operation | Endpoint/event | Scope | Adapter decision |
| --- | --- | --- | --- |
| Render one local widget | Local app HTTPS URL in OBS Browser Source (CEF) | No Twitch scope; OBS Page Permissions = None | One widget-scoped, read-only projection over local HTTPS; no OBS bindings/control API or remote assets. Native CA trust must be verified in exact OS/OBS/CEF versions before support claims. Never use HTTP or disable certificate validation. |
| Refresh widget data | Poll the local same-origin projection once per second | None | Measure the two-second target with eight active/enabled pages; a page unloaded while hidden fetches the latest state when it resumes. Queue open/closed state is projected only after remote synchronization is confirmed; pending, unknown, failed, or diverged states use the configured fallback. |
| Manage one widget | `POST/PATCH/DELETE /api/overlay-widgets` and capability lifecycle routes | Existing local panel session + CSRF + idempotency key | PostgreSQL model/migration, allowlisted style/source policy, SHA-256-only capability persistence, one-time HTTPS fragment URL and read-only `Authorization` projection are implemented; verify with current story evidence before calling FND-7 complete. |

Widget source scope is explicit: queue name/state/waiting count require `queue_id`; account label and the globally oldest called/in-service viewer are channel-wide; fixed text has no queue. Called viewer position is read from the persisted `previousPosition` audit snapshot. The projection returns only `sourceType`, the selected `value`, `fallbackText`, and style; it does not include widget/queue IDs, UID, token hash, or other business records. Capability reads take a PostgreSQL share lock through projection so deletion waits for an in-flight read and no read can return after deletion commits. One-time URL responses are not stored in idempotency replay records.

Native verification (2026-10-06): Ubuntu 24.04, OBS Studio 32.2.2 (Flathub), `obs-browser` 2.26.9 / CEF 127.0.6533.120. The Browser Source first rejected the app CA (`net::ERR_CERT_AUTHORITY_INVALID`); after importing the app CA into a temporary CEF NSS profile, it loaded over TLS 1.3 with security state `secure` and HTTP 200. No certificate bypass or HTTP fallback was used. `webpage_control_level=0` was read back from OBS (Page Permissions=None). Eight concurrent active sources rendered ten database update rounds (80 commit-to-DOM measurements); maximum was 905 ms, under the 2,000 ms target. The final authenticated run also verified bot stop/restart, stale-value recovery, Browser Source unload/reload, and capability rotation. The temporary trust import was removed afterward. OBS Studio 32.2.2 is installed and left available to the user. This evidence applies only to these Ubuntu/OBS/CEF versions; Windows and macOS are untested.

After the operator trusted the current local certificate in Chrome, panel-browser acceptance covered widget creation/editing, successful one-time clipboard copy, confirmed regeneration/revocation, deletion, and selection of a queue source backed by a disposable local PostgreSQL fixture. The fixture/widget were removed afterward; Twitch synchronization was not exercised. All generated capabilities were invalidated and the refreshed panel is empty. Unit/API coverage exists. The harness is `tests/e2e/overlay-browser.mjs`, exposed as `npm run test:e2e:overlay`; run it only with isolated local Compose, the stated OBS Browser Sources, and the app CA trusted by CEF.

| Concern | Contract |
| --- | --- |
| Database connection | PostgreSQL is reached by Compose service name `db`, never container `localhost`; runtime connection string is assembled from the mounted secret and is never logged. |
| Migration startup | `migrate` waits for healthy `db`; `bot` waits for successful migration completion. |
| Health | `/health` probes PostgreSQL and returns product version, Twitch integration state and `twitch_api_ping_ms`; authenticated channels, including ineligible ones, use a Helix `GET /helix/users?id=<broadcaster_id>` cached for 60 seconds. Missing Twitch credentials report `not_configured` and do not cause an endless restart condition. |
| Panel and OAuth transport | HTTPS on `https://localhost:${APP_PORT:-3000}`. Bootstrap persists a local CA and localhost leaf certificate in the secret volume, exports only the CA certificate under `.local/`, and mounts the server key read-only into `bot`. The operator imports the CA into the current-user trust store; no public host or proxy is required. |

Host certificate command review (2026-10-06): Linux uses GNU `install -D` to create the destination directory and install the public CA with mode 0644; quote `"$PWD/.local/localhost-ca.crt"` so paths containing spaces work. Windows uses PowerShell `Import-Certificate` with `Cert:\CurrentUser\Root`; `Resolve-Path` expands the project-relative input to an absolute path. macOS uses `security add-trusted-cert -r trustRoot -k ~/Library/Keychains/login.keychain-db "$PWD/.local/localhost-ca.crt"`; omit `-d`, which selects administrative trust settings rather than the default per-user trust settings. Command syntax was checked against [GNU Coreutils](https://www.gnu.org/software/coreutils/manual/html_node/install-invocation.html), [Microsoft Import-Certificate](https://learn.microsoft.com/en-us/powershell/module/pki/import-certificate), Apple's [Keychain Access certificate guide](https://support.apple.com/guide/keychain-access/kyca2431/mac), and the macOS [`security(1)` manual](https://manp.gs/mac/1/security). Windows/macOS native import and OBS trust have not been run by this project; only the Linux copy behavior and operator-reported Ubuntu trust-store command are evidenced here.
| Shutdown and data | SIGTERM/SIGINT closes HTTP/database work; Compose named volumes preserve the database and generated secret. Normal stop instructions never delete volumes. |
| ORM / transactions | Prisma 6.19.3 uses `PrismaPg({ connectionString })` with `PrismaClient({ adapter })`. Interactive transactions are short; a PostgreSQL transaction-level advisory lock serializes queue mutations, and database unique indexes remain the final concurrency guard. No network I/O occurs inside a transaction. |
| ORM migrations and tests | Prisma migrations are versioned and run by `prisma migrate deploy`; test contracts use real PostgreSQL and those migrations, not SQLite or a mocked Prisma client. |
| Image registry | `ghcr.io/gustavo8000br/subarushogun_gi_twich_bot` | GHCR makes the initial package private by default. Use a classic PAT with `read:packages` only during private pre-release testing; change package visibility to public before launch so product users can pull without registry credentials. The product never stores a token. |

The Twitch OAuth docs currently show `http://localhost:3000` in their examples ([OAuth guide](https://dev.twitch.tv/docs/authentication/getting-tokens-oauth/), [Get Started](https://dev.twitch.tv/docs/api/get-started/)). During this installation, the developer console rejected the configured `http://localhost:3000/callback` and required HTTPS. The product therefore uses `https://localhost:3000/callback` by default and documents the local CA trust step. The OAuth `redirect_uri` is kept byte-for-byte aligned across the Twitch app registration, authorization request, token exchange, and panel callback display.

## Verification boundary

The installed Twurple declarations were checked for `getCustomRewards`, `createCustomReward`, `getRedemptionsForBroadcasterPaginated`, `updateRedemptionStatusByIds`, `sendChatMessage`, the three EventSub listener methods, and refresh callbacks. The eligibility probe uses `getCustomRewards(broadcasterId, false)` so it counts every channel reward, not only rewards manageable by this application. An authorized live Helix user lookup was verified through `/health`; no real Twitch refund, reward mutation, chat delivery or EventSub operation was performed. SDK fakes can verify adapter behavior; they cannot prove a real Twitch refund or reward operation.
