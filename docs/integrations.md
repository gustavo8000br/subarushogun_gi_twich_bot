### OPS-7/OPS-9 command audience verification

The implementation distinguishes the `subscriber` badge on the current `channel.chat.message` from a current follower relationship. Subscriber/moderator/VIP claims use only target-channel badges on the current event. Follower checks use `GET /helix/channels/followers` with the event `user_id` and optional user scope `moderator:read:followers`, through the installed `@twurple/api` 8.2.0 `getChannelFollowers` method. The scope is requested only when a streamer selects a follower-based command threshold; missing scope, malformed identity, API errors, and inconsistent responses produce `unknown` and deny only dependent actions. Concurrent identical checks are coalesced; completed results are not cached or persisted. Optional OAuth consent is session-bound and one-time; staged policy and token are committed atomically after scope/identity validation. The product role ladder is application policy, not a Twitch-defined hierarchy. OPS-9 now stores only schema v3 minimum-role thresholds; runtime parsing of old role lists was removed. Its migration resets the command-policy setting and records an audit event without changing queues, entries, or credentials. This implementation is covered by unit and isolated PostgreSQL tests; no live Twitch authorization has been performed.

The reward requests must use `should_redemptions_skip_request_queue=false`, and incoming API/EventSub/SDK fields must be normalized at the adapter boundary. Twitch is authoritative for point status. Only the application that created a reward can manage its redemptions. Deleting a reward while redemptions are pending may fulfill them, so deletion must wait until cancellation is remotely confirmed.

This product uses EventSub WebSocket and Helix Send Chat Message with the streamer's account. It does not use IRC or a second bot account. Shared Chat may propagate user-token messages; the product must not promise otherwise.

### OPS-8 automatic connection recovery

The local API and panel start independently from Twitch network availability. Saved Authorization Code credentials remain in the local database; startup validation distinguishes temporary transport/server failures from a rejected refresh token or identity/scope mismatch. A valid saved refresh token is tried when Twitch rejects the access token, and rotated tokens are persisted before the integration resumes. Temporary auth, eligibility, or initial EventSub socket failures retry with exponential backoff, jitter, a 5-second initial delay, and a 300-second cap. The UI and `/health` expose `retrying` separately from `reconnect_required`; no raw error or token is projected. Once an EventSub socket has been established, Twurple owns persistent reconnect behavior; a genuine ready-after-drop triggers the existing reconciliation. Twitch's seamless `session_reconnect` does not create a competing socket. Durable outbox rows remain in PostgreSQL while the adapter is unavailable and resume through the existing workers. These behaviors are covered with controlled tests; the new recovery path has not yet been tested against an authorized live outage.

## FND-9 queue-mode and reward pause behavior (implementation in progress)

Product decisions and implementation status: streamer/moderator may add a viewer for free to any active queue after receiving a request; free-form chat is never enrollment. A reward-backed queue may transition one-way to local/manual mode. The request remains pending until Twitch confirms `is_paused=true`; failure/unknown preserves reward mode. After confirmation the app stops new redemption intake, keeps reward ID/origin as historical metadata, continues financial processing for existing redemptions, and durably cancels a redemption racing with conversion. ## Safe runtime diagnostics

Unexpected API failures return a generic localized message, stable `INTERNAL_ERROR` code and generated `referenceId`; that reference is also sent in `x-error-reference` and written to container logs. Structured records identify route/worker source, UTC timestamp, exception type and sanitized code. Reward workers log durable `retry`, `failed`, and `unknown` outcomes with the outbox error code, including outcomes without an escaping exception. Records omit raw exception messages/stacks, request bodies, chat/redemption payloads, UIDs, tokens, headers and database credentials. Correlate a panel reference or operation code with `docker compose logs --since=10m bot`. Financial/reward outcomes are authoritative in the persisted outbox; do not infer success from a timeout or missing response.
