## Reading this inventory

This is an initial surface-level map. It groups methods/routes into families and tests by file; it does not yet link each route to its DTO, revision, assertion, or individual state. The route/action-level expansion is a P1 OPS-15 deliverable, and all evidence remains pending.

The first detailed queue workflow slice is in [queue-route-action-inventory.md](queue-route-action-inventory.md). It maps current `queue-routes.mjs` actions, request fields, success shape/status, named route/Next tests, exact code-referenced catalog keys, and still-pending runtime/browser evidence for INV-05/06. It does not complete the remaining inventory rows.

- `Route contract` identifies the current Fastify route family and the concrete API paths confirmed in source. Request DTO details and revision fields must be linked from route contract tests before implementation acceptance; the table does not infer missing schemas.
- `Evidence status` is deliberately `Pending` until named tests and runtime/browser evidence are recorded for each action/state. Existing named tests prove only their own assertions.
- Product-facing catalog families are from the current English panel TSV and are present in all supported first-party panel catalogs (`en`, `es`, `pt-BR`); run localization validation to establish parity after catalog edits.
- Seven overlay source types remain supported: `account_label`, `called_viewer_display_name`, `called_viewer_position`, `queue_name`, `queue_state`, `queue_waiting_count`, and `fixed_text`. Previously saved `in_service_viewer_display_name` widgets are compatibility-projected as `account_label`.

## Gate sequence and proof rules

1. Establish safe Windows local database/runtime; never point a disposable test at product data.
2. Finish this inventory and link every row of the parent story's parity matrix to it. Record the route contract test and catalog keys actually used, not assumed.
3. Complete unit/route/DB/browser evidence. Separate test evidence from runtime evidence and mark unavailable prerequisites Pending.
4. Complete UX and Architecture review, then independent QA over this inventory, all parent AC, and the test audit.
5. Run Linux CI quality gates and native Windows installer/OBS checks as distinct environment gates.
6. Complete isolated rollback rehearsal and bilingual legacy-test audit.
7. Only then propose final cutover; vanilla deletion and OPS-15 completion remain subject to explicit owner authorization and all acceptance gates.
