### 2.3 LA-11 — legibility, minimum height, keyboard

**Status chip in native OBS** (white text on `rgba(0,0,0,0.72)`; chip background sampled at mid-height 4 px from the left edge to avoid the 3 px corner radius; text pixel = brightest pixel; WCAG 2.x ratio on the pixels of the OBS screenshot; `evidence/la11-*.json`):

| State | White scene | Gray scene (128) | Dark scene |
|---|---|---|---|
| Stale | chip pixel 144, **3.19:1** | chip 69, 9.59:1 | chip 0, 21:1 |
| Data unavailable | 144, **3.19:1** | 69, 9.59:1 | 0, 21:1 |
| Source unavailable | 144, **3.19:1** | 69, 9.59:1 | 0, 21:1 |

- Same widget in Chrome (production build, sRGB blending): 9.29 / 15.52 / 21. OBS composites the browser layer in linear light, so 72% black over white becomes 144 instead of 71. The ux-plan and the C4-a computation therefore overstate the OBS contrast: AC-13.5 ("any reading under 4.5:1 fails") is **not met on a white scene**.
- Measured fix candidates (CSS variable `--overlay-status-bg` overridden in the page DOM only, no source change): alpha 0.85 gives 5.25 / 12.82 / 21; **alpha 0.90 gives 7.11 / 14.74 / 21**; opaque gives 21 on all. Recommendation to `@dev`/`@ux-design-expert`: raise the default alpha to at least 0.90 (or opaque), then re-measure in OBS.
- AC-13.4: status text pixel (255,255,255) in the stale state, `statusOpacity` 1, value opacity 0.82. PASS.
- Normal state: chip hidden (`display: none`), widget keeps its size (scrollHeight = clientHeight = 65). PASS.

**Minimum height, 5 families, factor 1.4 (CA-12.5)**, font 32, box 65 px (`ceil(32 x 1.4) + 20`), stale/unavailable/data-unavailable: chip bottom minus box bottom = **0 px** in all 5 families in OBS (`chipBottomMinusBoxBottom` 0, bottom pixel row is chip color), and in Chrome. Natural line height measured: Chrome `system-ui` 1.344 (43 px at 32); OBS CEF 1.156 to 1.188 (DejaVu Sans for `system-ui`). The formula covers both with margin (needed 57 to 58 px vs 65). **Limit:** in the OBS Flatpak the four named families (Arial, Verdana, Georgia, Courier New) reported no platform font and gave identical metrics (37 px at 32), so they are fallbacks, not the real Windows fonts; the 1.4 factor is proven here for these fonts only. PASS with that limit.

**Keyboard walk (real Chrome, production build, `/widgets`):** Tab reaches the first "Editar" in 13 stops; Enter opens the dialog and puts focus on "Fechar"; Tab cycles through all 26 stops inside the dialog (23 fields, Cancelar, Salvar widget, Fechar) in visual order and wraps (focus trap), every stop with a 2 px visible outline; the Height field has `aria-describedby="widget-height-hint"` and the hint shows 65 px for font 32; typing font 48 updates the hint to 88 px and (height 65) shows the non-blocking message `role="status"` "Esta altura é menor que 88 px..."; height 40 keeps it; height `auto` removes it; "Salvar widget" stayed enabled in all cases; Escape closes the dialog and focus returns to "Editar". PASS. Finding D-4 (low) came out of this walk.

Not executed: screen reader (excluded, LB-05); the **mobile checklist** named in the ledger row (no device or emulation session was run).
