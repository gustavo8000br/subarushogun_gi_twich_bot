## 2. Findings, prioritized

Priority: P1 = fix before the area is called accepted; P2 = fix in the next UX slice; P3 = polish / record only.

### P1

None. No finding blocks the one-time link flow itself, which is the S-13 safety-critical part.

### P2

**F-01 — Editor dialog discards the draft on an accidental backdrop press, Escape or the close button, with no confirmation.**
`widgets-page-content.jsx:287` (`onMouseDown` on the backdrop closes the editor), `:118-121` (Escape closes it), `:289` (× button). Observed: typing in the "Fixed text" field and pressing the backdrop closed the editor and lost the text, no warning. The widget editor has 19 style fields, so the cost of an accidental loss is high, and it contradicts the spirit of the spec rule that secrets dialogs resist accidental dismissal. Recommendation: if the form is dirty, ask for the same two-button confirmation used by the link dialog ("Discard changes?" / "Keep editing"); do not close on `mousedown` of the backdrop when dirty. Reuse the existing `confirmation` machinery (`:81`, `:315`).

**F-02 — Destructive and link-invalidating confirmations do not say which widget.**
`widgets-page-content.jsx:315`; catalog `panel.widget.confirm.{regenerate,revoke,delete}`. Observed: the `alertdialog` has no `aria-describedby`, its text does not contain the widget identity, and the cards are visually and non-visually identical (F-03). With two or more widgets, "Delete this widget?" is ambiguous, and regenerate/revoke break a live OBS source. Recommendation: add the card identity (source label plus the 8-character id already shown in `panel.widget.card_details`, plus the queue title when present) as a line in the dialog, and `aria-describedby` pointing to the text. Keys to add in the three catalogs (see section 4).

**F-03 — Cards have duplicate headings and duplicate button names.**
`widgets-page-content.jsx:275` (`<h3>` = source label), `:278-281` (buttons "Edit", "Regenerate link", "Revoke", "Delete"). Observed: two fixed-text cards give two `h3` "Fixed text" and eight buttons whose accessible names repeat. A screen-reader user navigating by headings or by the buttons list cannot tell which card a button belongs to (WCAG 2.4.6 Headings and Labels, 4.1.2; the repeated names also make the voice-control "click Delete" ambiguous, 2.5.3 Label in Name is still satisfied if the visible text stays in the name). Recommendation: keep the visible text and extend the accessible name: `aria-label` or `aria-describedby` linking each button to the card heading/id (e.g. "Delete, Fixed text, widget 1111aaaa"). Prefer `aria-describedby` to a visually available `id` on the details paragraph so no new catalog strings are needed for the description part. Make the `h3` unique by appending the id fragment in a visually subtle way.

**F-04 — Focus after deleting a widget lands on an unrelated button.**
`widgets-page-content.jsx:132` restores `previousFocus` only if still connected; the delete button is removed with its card. Observed: after deleting the second card, focus ended on `Revoke` of the remaining card (arbitrary, not designed). The regenerate path has an explicit target (`:136-144`), delete and revoke do not. Recommendation: extend the `focusTarget` mechanism: after delete, focus the next card's `edit` (or the previous one, or the `create` button / empty-state button when none remains); after revoke, focus that card's `generate` action (it replaces `regenerate`). This is consistent with the dialog-return rule in `ux-plan-widget-link-and-spec.md` section 1.2.

**F-05 — Form-control borders do not reach 3:1 against the surface (WCAG 1.4.11 Non-text Contrast).**
`panel.css:62` (inputs, selects, textarea: border `var(--border, #292a36)` on a `#0d0e14` field inside a `#12141b` panel). Computed: border/surface 1.30:1, field background/surface about 1.05:1, so the boundary of a field is not perceivable by low-vision users; the focus ring is fine (`panel.css:21`, 6.71:1 on `#15141d`). `--border` and `--text-primary` are also used with fallbacks but are never defined in `:root` (`panel.css:2-11` defines `--line`, `--text`), so the fallbacks silently apply. This is panel-wide (also `account-settings-form`, `command-policy-controls`), not only Widgets. Recommendation: one token decision (needs owner approval; "NEVER modify design tokens without explicit approval"): a control border of at least `#6b6e82` on `#0d0e14` (about 3.7:1) and define `--border`/`--text-primary` or replace them with the existing tokens.

### P3

**F-06 — Width/height fields use `inputMode="numeric"` but accept `auto`.**
`widgets-page-content.jsx:363`; label "Height (px or auto)". On a phone the numeric keypad has no letters, so `auto` cannot be typed (observed attribute `numeric` at 390x844 in es and pt-BR). Recommendation: drop `inputMode` or use `text` with a `pattern`/validation message. Low severity because `auto` is also the stored value and the default is numeric.

**F-07 — Terminology drift for the OBS source name.**
Catalog: `panel.widgets.link_help` (es "fuente Browser", pt-BR "fonte Browser") against `panel.widget.obs_help` and `panel.widget.height_hint` (es/pt-BR "Navegador"). The same OBS object is named two ways in the same view. Recommendation: use the OBS UI term of each language ("Navegador" in es and pt-BR OBS builds, "Browser" in en) everywhere, keep "Page Permissions" in English because OBS shows it in English (current text does). Needs the native-speaker pass already listed as a deduction. Also check whether `panel.widgets.link_help` is still referenced; the dialog uses `link_lifetime_help` (grep before editing).

**F-08 — Targets in the editor form are 40-42 px high.**
Observed at 390x844: all inputs/selects 40-42 px. WCAG 2.5.8 (AA, 24 px) passes; the project's own touch rule for these dialogs is 44 px (`.widget-link-dialog .button`, `panel.css:87`, and the E2E asserts >= 44). Recommendation: `min-height: 44px` on `.widget-editor-form input/select` (`panel.css:62`) under `@media (max-width: 760px)`. Cosmetic.

**F-09 — Eyebrow labels are 9 px.**
`panel.css:114` (`.eyebrow` 9 px, 6.54:1 on the dialog background, passes contrast but is below any comfortable reading size) and `:131` (`.section-heading .eyebrow` `#777987` on `#0c0d12` = 4.50:1, exactly at the AA limit for small text; any change to the background breaks it). The one-time dialog uses the same class for "ONE-TIME LINK". Recommendation: 11 px minimum and `#8a8c9c` or lighter for `:131`.

**F-10 — Spec wording: overlay language.**
`docs/front-end-spec/interaction-and-content-rules.md:5` says the language is shared by "the panel and chat replies"; the repository also ships `overlay` catalogs (`apps/shared/localization/catalogs/overlay`) and `app/(overlay)/layout.jsx:8` hard-codes `lang="pt-BR"`. Either state that the overlay language follows the product language (if the renderer does) or that it is out of scope, and make the overlay layout's `lang` follow the locale if overlay text is localized. Check before editing; this review did not run the overlay in OBS.

**F-11 — Spec wording: the bundle boundary has a test, not a lint rule.**
`docs/front-end-spec/accessibility-and-layout.md` ("Overlay code must not import panel modules") is true today only because of `tests/e2e/overlay-bundle-boundary.mjs`. Recommendation: say "verified by the bundle-boundary E2E" in the spec, or add an ESLint `no-restricted-imports` zone for `app/(overlay)/**` (a `@dev` change; out of scope here).

**F-12 — Link dialog: small a11y refinements (not defects).**
`widget-link-dialog.jsx:44` repeats `aria-modal="true"` on a native modal `<dialog>` (harmless, redundant); `:60` the field label is a `span` linked by `aria-labelledby` only when revealed (the masked state exposes "Local widget URL Link hidden" as plain text, which is read correctly in the accessibility tree); the Show/Hide toggle swaps its label instead of using `aria-pressed` (acceptable: a swapped label is the recommended pattern when the control is not a toggle in appearance). When the dialog changes from the link view to the confirmation view the content is replaced and focus moves to "Back to the link" (observed), so a screen-reader user hears the button before the heading; the dialog name changes through `aria-labelledby`, which most readers announce on focus entry inside a named dialog, but this was not confirmed with a real screen reader. Recommendation: confirm with NVDA/VoiceOver in the `@qa` pass; if the title is not announced, move focus to the heading (`tabindex="-1"`) and let the user Tab to the buttons.

## 3. Checks that passed (observed in Chrome or computed)

- **Secret handling:** while masked, the URL is not in the DOM; no secret in `aria-live` regions; two permanent empty live regions (`role="status"` and `role="alert"`) so announcements are reliable.
- **Dialog behavior:** `closedby="none"`; Escape from the link view opens the confirmation; the confirmation focuses the least destructive action ("Back to the link"); initial focus on "Copy link".
- **Focus visible:** `:focus-visible` outline 2 px `#a78bfa`, 6.7:1 on the dialog background.
- **Contrast:** primary button white on `#67469e` = 7.13:1; secondary `#d2cfdd` on `#171820` = 11.54:1; error text `#ffd9dd` = 14.11:1; body text in dialogs `#d1cfda` = 11.87:1.
- **Responsive 390x844 (es and pt-BR):** no horizontal scroll on the page or inside the editor; link dialog 362 px wide at x=14, no overflow; card action buttons 44 px high; the dialog buttons stack under 480 px (`panel.css:88`).
- **i18n:** `document.documentElement.lang` follows the product locale (`panel-provider.jsx:141`); es and pt-BR dialog texts fit without truncation; the three catalogs contain every key the dialog uses.
- **Loading, empty, error states:** `role="status"` loading, empty state with a primary action, `role="alert"` load failure with the reference line and a refresh action (`:267-269`), consistent with `ux-plan-e7-reference-id.md` (same `panel.widget.notice.reference` / `referenceId` pattern, same allowlist `^[A-Za-z0-9_.-]{1,64}$` at `:14`).
