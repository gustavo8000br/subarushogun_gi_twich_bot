## 2. Findings in detail

**M-1 (medium) compose-runtime flake.** Run 1 failed at `tests/integration/compose-runtime.test.js:653` (`created.json()`, "Response body is not available for a response that was navigated away from"). This is the known TS-15 family, but at a new line and tied to FT-23: the form now leaves for `/queues/` right after the 201, and the test still calls `created.json()` on the response after the click. `@dev`'s README records the same failure in its first full run and a "fix" that was the `waitForURL`/focus edit further down (diff lines 670-690); that edit does not protect line 653. Not a product defect (the DOM and URL outcome are tested by the Chromium scripts 3/3), but a test that fails 1 in 2 full runs will break the CI. Recommendation: read the body inside the response handler (`page.on('response')` plus `response.json()` before navigation, or `route.fetch`) and rerun the full suite 3 times before the FT-23 commit. The CI is the confirmation, not the proof.

**M-2 (medium) mutation coverage.** Not reproduced: M2, M3, M5, M7, M8, M11, M15, M16, M19. They are covered by named tests in the plan but this gate did not prove them.

**L-1..L-7:** see the YAML header.

## 3. Judgement of the decisions (a)..(i)

**(a) Existing tests altered; is the contract stricter?**
- `qra-postgres-fixtures.test.js` ~509-529 (the plan said these fixtures stay unchanged; the Orion decision of 2026-10-30 option A overrode it, recorded in the test comment). Before: status 200, body `{status:'not_cancelled', reason:'queue_deletion_cancel_verification_failed', queue:{...}}`; task `unknown`, `lastError ..._failed`; audit rows `requested` (with `actorId`) and `not_confirmed` (without `actorId`, reason `_failed`). After: status 409, `code: QUEUE_DELETION_REMOTE_DELETE_ATTEMPTED`, body does not contain the adapter message (new); task `unknown`, `lastError ..._unavailable`, payload flag kept; audit `not_confirmed` now with `actorId` and reason `_unavailable`. Removed: the response `queue` snapshot and the `reason` field (a 409 carries only `code`). Stricter on safety (leak canary, actor) and on the refusal, looser nowhere that matters. New twin case (no DELETE attempt): 200 `not_cancelled` with `_unavailable`, task restored, audit with actor, canary absent.
- `queue-repository.test.js` ~1912: before `resolves.toMatchObject({status:'not_cancelled', reason})`; after `rejects.toMatchObject({code:'QUEUE_DELETION_REMOTE_DELETE_ATTEMPTED'})`, the task still `unknown` with its reason and flag, plus a new audit assertion (`actorId`, `nextState`, `reason`, `safeDetail {restored:false, previousStatus:'unknown'}`). Stricter. Other edits in that file only pass `{ actorId: 'operator-123' }` to `retryOutboxManually` (the new required argument; `ACTOR_REQUIRED` otherwise).
- U26-06 `canCancelDeletion`, FT-23 tests in the Dev Notes, PG36-05 401 row: read; all assert more than before (server flag instead of the heuristic, closed lists, canaries). The 401 row is L-2.
- `compose-runtime.test.js`: the creation flow now waits for `/queues/` and the focus on the queue title, the dialog assertions use the new title and buttons. Equivalent coverage, but it is the source of M-1.

**(b) PG36-16 and "without reopening the queue".** Partly. The test proves the open task ends `unknown('reward_open_reward_diverged')`, `remoteSyncStatus = open_unknown`, no write to Twitch, no `open_state_confirmed`, and that a second open request answers `open_unknown`. It does not assert `isOpen`; `setQueueOpen(true)` leaves the local flag true while the sync is pending/unknown. In a Channel Points queue entries come from redemptions, which cannot happen on a reward that is gone, so no entry is admitted (reasoned, not tested). Accept with L-1: add an `isOpen` assertion or document the flag semantics.

**(c) Four singular texts** (`confirm.delete_local.one`, `confirm.delete_converted.one`, en/es/pt-BR counted as the four families). Grammatically correct derivations of the existing plural; they match the plan's pattern for `confirm.delete.one`, but the plan lists only that key (L-3). Needs a recorded `@ux-design-expert` acknowledgement; the inherited "reward" in pt-BR is not new.

**(d) `apps/web/app.js` plural change.** One call site; `panelTextPlural` gains an optional `values` argument (default `{}`), so older callers are unchanged. Dead code after wave 4; acceptable. Covered indirectly (localization and lint green); there is no browser test of the legacy panel in this gate.

**(e) F18 brought into FT-26.** Accepted. `enqueueRewardDeleteIntent` reuses the single `reward.delete` row and fails closed on an unexpected status; M18 (back to `tx.outbox.create`) is caught by PG36-09 and PG36-09b. Needed by the resume path of FT-26, so the order FT-26 before FT-36 is sound.

**(f) Paused task restored after 401.** AC 16 says the deletion "stays blocked with the auth state visible and re-arms after re-authorization". The re-arm selects only `status 'retry'` with `twitch_authorization_required` (PG26-06 proves it for `reward.delete`). A pause task that a cancel read restored to `unknown`/`failed` is not re-armed and needs "retry now". The literal AC is met for the case it names (401 during deletion); the restored-pause case is a documented edge, not a violation. Recommend writing it as an explicit limit in the story.

**(g) Lock order retryOutboxManually x requestQueueDeletion.** `retryOutboxManually` locks the outbox row then updates the queue row; begin/request take the queue advisory lock then `FOR UPDATE` on the `reward.%` rows. I found no reachable cycle in a read of the code (the begin transaction does not write the queue row before the outbox rows), and PostgreSQL would abort one side with 40P01 (a generic 5xx), never hang. No test exercises it. Accepted as the `@data-engineer` did; not proven by this gate.

**(h) Fixed clock 2030-01-01 and time bombs.** The three new PostgreSQL files inject a clock fixed at `2030-01-01T12:00:00Z`; the only DB-clock use in `queue-repository.mjs` is one `updated_at = now()`, so no comparison against the real clock was found. Fixed dates elsewhere in `tests/`: `queue-repository.test.js` 246 (2026-10-11), 1455/1471 (2026-10-06), 1486 (2026-04-21); `queue-repository-chat.test.js` 7/54 (2026-10-03); `overlay-widget-repository.test.js` 246 (2026-01-02); `compose-runtime.test.js` 268/780 (2026-10-20); `tests/helpers/twurple-real-instances.mjs:19` (2026-10-27). All feed an injected clock or a value parameter, not the database clock, so none is a time bomb today. Sweep limits: unit tests with fakes were not audited line by line; the 2030 constant itself becomes a bomb only if a row default `now()` is compared with it after 2030.

**(i) Audit catalogue and leaks.** The key sets in `audit-catalog-confirmation.md` match the allowlists asserted by PG36-13 (`requested`: rewardId, operationId, operationType, deletionState, blockReason, requestMayHaveReachedTwitch, safeToDelete; `cancelled`: rewardId, operationId, remoteSyncStatus, isPaused, cancelledTasks, financialTasksLeftRunning; `not_confirmed`: rewardId, operationId, restored, previousStatus) and PG25-10 (retry_scheduled, attempts_exhausted, confirmed_by_reverification, retry_requested, resolved_manually). `operationDto` projects only enumerated reasons (`attempts_exhausted`, `authorization_required`, `manual_contradicted`) and a UUID-checked `blockingQueueId`; the deletion projection is built by `getQueueDeletionProjection` from enumerated values. Canary tests (adapter message, token-like strings) pass in the route and PostgreSQL tests. No raw UID, token, adapter message or chat text reaches `/api/operations` or `/api/state` in the code path read; this is static reading plus the tests, not a live-service capture.
