## Story

As a streamer,
I want calls, permissions, attendance, and removed Twitch rewards to update the application consistently,
so that queue operation remains accurate without losing history or misrepresenting financial outcomes.

## Scope and decisions

This story groups the four reported regressions in issue #57:

- Individual calls must honor the configured account auto-switch and refresh the overlay's current-account projection.
- Edited command permissions must be sent, persisted, and visible after reloading the panel.
- A called viewer's `!<queue> present` acknowledges presence and stops the absence countdown, but does not start service; only the streamer performs that transition.
- A reward confirmed absent by a successful authoritative Twitch read retires its local queue from active operation while retaining history and financial state. API/auth/network failures are not evidence of absence.

**Approved data contract (Dara):** Add nullable PostgreSQL `timestamptz` `callAcknowledgedAt` (`call_acknowledged_at`) additively, with no backfill. Presence, notification-result handling, and timeout share the same queue lock and re-read persisted state before deciding. Outbox claim revalidates call status and acknowledgment under that same queue lock. Soft retirement uses existing queue fields `lifecycleStatus=deleted`, `deletedAt`, `isArchived=true`, `isOpen=false`, and `remoteSyncStatus=deleted`; retain `rewardId` and all history, and write an audit record containing the observed version. Do not add a queue column or change financial state for reward absence. Tombstone reconciliation covers all reward-backed deleted modes, using a cursor, lease, and fair bounded batches. A partial-index widening is conditionally approved only after natural `EXPLAIN (ANALYZE, BUFFERS)` on a representative disposable PostgreSQL dataset; do not force planner settings. Before any persistent-database change, take and verify a compatible snapshot and define rollback. A missing reward must never become financial confirmation.

## Acceptance criteria

1. **Individual call and account/overlay projection:** When queue settings enable automatic account switching, an individual call selects the called viewer's configured account using the same policy as other supported call paths. The updated current account is reflected in the overlay without a manual page reload. Tests verify the call's persisted state and the resulting fresh overlay projection; a call without an eligible account does not invent or select one.

2. **Permission PATCH and reload:** Editing a command permission produces a PATCH payload containing the edited policy and current expected revision. A successful response persists that exact policy; a fresh panel/API load shows it and the new revision. A real-PostgreSQL integration test using actual migrations exercises PATCH followed by a fresh read/reload and verifies the persisted value/revision. Regression coverage also exercises the panel's permission collector with the actual command-card/section shape. A genuine edit cannot be reported as “no changes”; a true no-op remains a no-op.

3. **Idempotent, race-safe presence acknowledgment:** Only the called viewer can use the applicable `!<queue> present` command while their call is awaiting a response. The first valid command durably sets nullable `callAcknowledgedAt` (`timestamptz`, additive migration, no backfill) and stops the absence countdown without moving the entry to in-service, completing it, or calling the next viewer. Repeated commands are idempotent. Presence, timeout, and notification-result handling share the same per-queue PostgreSQL lock and re-read persisted state before deciding. Outbox claim revalidates call status and acknowledgment while holding that same queue lock. An already-dispatched external message cannot be recalled; existing outbox/unknown-outcome rules remain in force. Real PostgreSQL integration tests with migrations cover concurrent presence/timeout/notification-result, outbox claim revalidation, duplicate acknowledgment, and restart/replay.

4. **Confirmed reward absence and explicit local-only deletion:** Automatic reconciliation may mark a reward absent and soft-retire its queue only after a complete, successful, authoritative Twitch response for the correct channel/owner proves that the exact managed reward ID is absent. A successful response containing the reward keeps the queue active. HTTP 401, 403, 429, 5xx, timeout, network failure, malformed/incomplete response, or unknown ownership must leave remote state unknown/failed and remain retryable/diagnosable; none is evidence that Twitch deleted the reward.

   When synchronization fails or remote state is unconfirmed, the panel offers the streamer **Delete from this panel anyway** after two explicit confirmations: an initial confirmation modal followed by a separate final confirmation clearly labeled as a local panel deletion. Both explain that the Twitch reward may still exist. The first confirmation obtains a short-lived server-side challenge/nonce bound to the queue, local-delete action, expected version, and current remote status. The challenge is single-use; replay is idempotent. On final confirmation, one transaction validates and consumes the challenge, version, and eligibility under the shared queue lock, deletes the queue from the active panel and closes its local intake (`lifecycleStatus=deleted`, `deletedAt` set, `isArchived=true`, `isOpen=false`), and removes it from active-operation controls. Preserve the exact current `remoteSyncStatus`, including `pending_*`, `failed`, `unknown`, `diverged`, and `delete_pending`; never set it to `deleted`, and add no migration or new status for this action. Deleted queues are excluded from the active projection, and confirmation copy labels the preserved value as historical/unverified rather than an active sync. Preserve `rewardId`, slug, QueueKey/aliases, tombstone, entries, redemption references, audit/history, every outbox row, and all financial state. The audit record identifies the explicit local override, reason, and observed version. The action sends no Twitch delete and does not claim remote deletion, cancellation, fulfillment, or financial success.

   Queue locking is shared with outbox claim and follows queue lock → outbox-row lock/re-read. A reward-backed tombstone receives no mutation claims. Pending, unclaimed `reward.*` operations must not execute after the archive commits; cancel them while retaining their rows when it is certain they were not sent, and record an unknown outcome when they may have reached Twitch. Any `reward.*` operation already in `processing` blocks finalization with a retryable conflict, even if its lease appears expired. Finance operations are not canceled, resolved, or otherwise changed. Pending/unknown redemptions and outbox work remain recoverable/reconcilable even when the entry is terminal. Redemption ingestion for a tombstoned `channel_points` queue must not be discarded as unmanaged. A `create_unknown` queue without `rewardId` is ineligible until exact remote-create recovery binds the reward/tombstone; the panel explains the block. Concurrent changes cannot release keys, lose work, or cause an invalid archive.

   For automated confirmed absence only, soft retirement uses existing lifecycle fields `lifecycleStatus=deleted`, `deletedAt` set, `isArchived=true`, `isOpen=false`, and `remoteSyncStatus=deleted`; it retains `rewardId` and the same history/financial records and writes an audit record with the observed version. Neither path adds a queue column or changes financial state merely because the reward is absent or the local queue was archived.

5. **Bounded tombstone reconciliation:** Reconciliation scans every reward-backed queue tombstone (`lifecycleStatus=deleted` and `rewardId` present), across supported queue modes and exact retained remote statuses, including pending/unknown redemptions even when their entries are terminal. It uses a persisted cursor and lease with fair bounded batches, safe restart/replay, stale-worker protection, and priority for active queues; scanning never reactivates an archived queue. It must ingest redemptions for tombstoned `channel_points` queues rather than discard them as unmanaged, while avoiding mutation claims for tombstones. A partial-index widening is permitted only after natural `EXPLAIN (ANALYZE, BUFFERS)` selects that index on a representative disposable PostgreSQL dataset with normal planner settings; do not force planner settings. If needed, the index is migration-managed and validated with real migrations. Before any persistent-database change, take and verify a compatible snapshot and define rollback. Tests use an isolated disposable PostgreSQL instance; no active product volume is used.

6. **Regression, localization, and quality evidence:** Tests are added before behavior changes and record observed Red/Green results. User-facing strings changed by this story remain equivalent in English, Spanish, and pt-BR. The implementation passes project lint, typecheck, full test suite, static review, localization/version validation, Compose validation where affected, and `git diff --check`; QA records a score and maps each AC to evidence.
