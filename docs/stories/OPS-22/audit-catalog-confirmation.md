## Findings

**C-1. Lock-order inversion in `retryOutboxManually` (pre-existing in shape; opinion below).** See the next section.

**C-2. Two spellings of the 401 marker on reward tasks.** The reward worker and the projection use `twitch_authorization_required` as the `last_error` of a reward task held by a 401 (`queue-deletion-policy.mjs:13`, `queue-action-state.mjs:80`, rearm query `queue-repository.mjs:2076`). A 401 on the **cancel read** passes `authorization_required` (`queue-service.mjs:87`), and `failQueueDeletionCancellation` writes `lastError: errorCode` (`queue-repository.mjs:1054`), also for a task whose previous `last_error` was the worker's marker (`payload.cancelVerification.previousLastError` is saved at begin but never restored). Consequences: the restored task loses its `twitch_authorization_required` marker, so `blockReason` for it can fall to `reward_operation_unconfirmed` or `null`, and `rearmAuthorizationBlockedOperations` no longer selects it (it keeps its old `next_attempt_at`, so it is still retried by the normal schedule; delay, not a stuck row). Nothing unsafe happens. Fix (small, `@dev`): when the cancel read returns 401 on a reward task, store `REWARD_AUTHORIZATION_REQUIRED` in `last_error` and keep `authorization_required` only as the response `reason`/audit `reason`; or restore `previousLastError` on any non-conclusive read. Test: PG36-01 5xx variant keeps asserting `queue_deletion_cancel_verification_unavailable` (by design in the plan); add a 401 variant asserting the marker.

**C-3. `financial.operation_retry_requested` is also written for `reward.*` tasks.** The `financial.` prefix is a misnomer for reward tasks (the convention would be `queue.*`), but the 2026-10-30 note recommended one event with `operationType` telling them apart, the allowlist test already covers both shapes, and a rename would move a name already in the plan and tests (PG25-07, PG25-10). Decision: **keep**, as a documented exception. Condition: readers must filter by `safeDetail.operationType` when they care; for reward tasks `queue_id` is `entity_id` (`:2615`) and `redemption_id` is `NULL`; the key set per type is asserted by `@qa`. If the owner later wants a neutral name, the candidate is `operation.retry_requested`, with a read alias for the old one; not recommended now.

**C-4. `QUEUE_DELETION_REMOTE_DELETE_ATTEMPTED` audit trail.** The refusal is thrown by the service after the fail call, so the audit has `queue.deletion_cancellation_not_confirmed` with `restored`/`previousStatus`; there is no separate row for the refusal and none is needed. `@qa` proves the order (restore first, then refuse) in PG36-05.

**C-5. Best-effort rearm after re-authorization (`integration.mjs:340-342`).** Coherent with the project error policy (AGENTS/CLAUDE: unexpected failures yield a generic localized text plus a `referenceId`, logs without internals, Twitch errors stay in the outbox in a safe state, absence of an answer never becomes a confirmation). The tokens are already stored when the rearm runs; a rearm failure only means the held work waits for its normal schedule (financial `unknown('authorization_required')` stays terminal until the next re-authorization or "retry now", reward tasks stay in `retry`), so it neither loses data nor confirms anything. `reportDiagnostic` carries only `source` and the error through the project diagnostic channel (test `twitch-integration.test.js:448`). The OAuth reply must not fail because of it: correct. Condition: the diagnostic is the only signal, and a persistent failure leaves financial tasks in `unknown('authorization_required')` visible in Operations (they are listed), so the operator has "retry now" as the way out. **CONFIRMADO COM CONDIÇÃO**: `@qa` proves that a thrown rearm still answers 200 to the callback and the tokens stay stored (exists, `twitch-integration.test.js:403-448`), and that the rearm is idempotent when called twice (second call changes 0 rows, writes 0 audit rows).

## Opinion: lock-order inversion between `retryOutboxManually` and `requestQueueDeletion`

**Facts.** `requestQueueDeletion` (and begin/fail/confirm of the cancel, `claimNextRewardOperation`, `lockProcessingRewardTask`, `rearm`, `resolveUnknownFinancialOperation`, `resolveRedemption` confirm) take the per-queue advisory lock first (`lockQueue` `:36-38`, `withQueueTransaction` `:139-144`) and then row locks. `retryOutboxManually` takes `FOR UPDATE` on the outbox row first (`:2597-2598`) and only then touches the `queue` row (`findUnique`/`updateMany`, `:2626-2635`), **without the advisory lock**. The shape is not new: at HEAD the method did `findFirst`, `updateMany` on the outbox row and then the queue update, with the same order; FT-25 added the explicit `FOR UPDATE`, it did not create the inversion.

**Is a deadlock reachable?** A cycle needs two transactions each holding what the other wants. I enumerated the writers of the same outbox row X (status `unknown`/`conflict`/`failed`) and of the queue row Q:
- retry holds X and wants Q. The only transactions that hold Q and might want X are the ones that update `queue` and then write the outbox row: `requestQueueDeletion` (advisory, `queue.update`, then `enqueueRewardDeleteIntent` on a **`cancelled`** `reward.delete` row, or `create`) and `confirmQueueDeletionCancellation` (locks all `reward.%` rows first, so it waits on X **before** touching Q, it never holds Q while waiting on X). `requestQueueDeletion` can only run on a queue that is not `deleting`, and the row it can lock is `cancelled`; retry's lock predicate requires `unknown/conflict/failed`. The two row sets are disjoint, so no cycle exists with the current statuses.
- Worker paths hold the advisory lock and a **processing** row; retry's X is not processing, so a worker never waits on X, it can at most make retry wait for Q until the worker commits. A wait, not a cycle.
- Interaction with the cancel is safe by construction: once begin moved the row to `cancel_verification`, retry's predicate no longer matches (returns 0, route answers `OPERATION_RETRY_UNAVAILABLE`); if retry commits first, begin sees a `pending` row. Retry bumps `queue.version`, so a confirm that already read the version gets `QUEUE_DELETION_CANCELLATION_STALE` (CAS), then restores the status. Both are safe outcomes.
- If PostgreSQL ever did detect a deadlock (`40P01`), it aborts one transaction; a manual retry is a single operator click, nothing is partially written (one transaction), and the operator can repeat it.

**Recommendation: ACCEPT for this bundle with the justification above, and OPEN a follow-up item (not blocking), owner `@dev`, to remove the inversion by construction.** The fix is local: in `retryOutboxManually`, resolve the owner queue first (`entity_id` for `reward.*`, `redemptions.queue_id` for financial) with a plain read, call `lockQueue(tx, queueId)` and only then run the `FOR UPDATE`, re-checking the status after the lock (the existing `WHERE status = <read>` and `count === 1` guards already do). That gives one global order (advisory, then rows) for every path. I do not ask for it now because (a) no cycle is reachable today, (b) it changes a transaction that PG25-13 and PG25-07 already pin, and the bundle is going through one QA gate, (c) it needs one more test (two-connection barrier between retry and `requestQueueDeletion`/begin). Revisit as a **must-fix** if any new writer of `reward.delete` rows in `unknown/conflict/failed` is added to a path that holds Q.
