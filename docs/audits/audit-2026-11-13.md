**Author:** `@architect` (Aria), model Claude Opus 5.5 (reason recorded to the owner by the orchestrator: cross-checking contradictions between 17 batch reports and reviewing the OPS-31 financial design). **Date:** 2026-11-14. **Branch read:** `chore/emergency-snapshot-2026-11-12` (HEAD `5da50c2`, 19 commits ahead of `origin/main`, not published).
**Method:** reading of the 17 batch reports (P1/P2 in full, P3 by scan) written by `@qa` between 2026-11-13 and 2026-11-14, followed by my own sample verification (file:line) of every critical finding. **Read-only**: no product file, issue, PR or branch was changed; no test battery, no Docker, no internet. The only side effect is this file and its pt-BR pair.
**Evidence class:** static reading of code, documents and Git metadata. Nothing was executed against PostgreSQL, Twitch, a browser or OBS. Where this report says "verified", it means "verified by reading at the cited line".

## 1. Executive summary

- The product code is in better shape than its documentation. No double grant and no double refund were found in the money paths; the financial worker reads before it writes, uses leases and a `UNIQUE` idempotency key, and never leaks error text.
- The **largest risks are outside the product code**: (1) a folder of the orchestrator's personal memory with Claude session identifiers is published on the public `main`; (2) the local working branch carries a non-gated WIP commit with 42 more memory files in its history, so pushing it as is would re-expose them; (3) the `@devops` agent definition contains Git rules from another project that allow a force push to `main`; (4) the push-blocking hook is not versioned; (5) `release.yml` publishes a release automatically on every push to `main` once the stage is `rc` or `stable`, which contradicts the owner rule that every release needs an express OK.
- **Document truth is the most widespread problem**: stories in a false state (OPS-22, OPS-26, OPS-21, OPS-12, OPS-18/19, OPS-20), the branch `legacy` and the vanilla panel described as existing, ten user-facing documents saying that no public release exists, and stale handoffs that order dangerous actions (resume a merge already done, keep the vanilla panel).
- **Money design**: the OPS-31 design cannot start as written. Four code paths cancel every `UNFULFILLED` redemption by rule, without knowing any "held" state; the proposed `CHECK` would make the queue-deletion task loop forever; direct `called → completed` has no group-lookup moment. Three current defects (clear/delete fails with a redemption in service, `conflict`/`failed` have no exit, the deletion task has no safe state on exception) must be fixed first.
- **Beta ledger**: 22/32 is arithmetically right but not uniformly applied. Under a consistent reading the firm count is **20/32** with two provisional credits; and the guard (features 7 to 10 must be Y) still fails on features 7 and 9 regardless of the count.

## 6. Definitive map of the redemption flows (today, corrected)

Base: b8 section 1, re-verified at `entry-transitions.mjs:4-66`, `queue-service.mjs:10-23`, `queue-repository.mjs:376-391, 836-919, 1600-1622, 1748-1791, 1863-1932, 2296-2312, 2619-2623`, `reward-worker.mjs:256-338, 363-370`, `outbox/loop.mjs:15-30`, `queue-routes.mjs:24-30`.

### 6.1 Entry of a redemption

```
Twitch: viewer redeems (UNFULFILLED, points already spent)
  -> EventSub add, or reconciliation (startup, reconnect, every 5 min, operator)
  -> importRedemption (under the queue advisory lock)
       refused (mode in transition, Channel Points off, queue unavailable/closed, invalid UID,
                duplicate active entry) -> redemptions row + redemption.cancel  [legitimate]
       accepted -> redemptions(observed) + entry `waiting`, no financial task
       already recorded -> no-op; terminal before add -> row without entry
```

### 6.2 Transitions and financial decision

Financial key: `financial:{redemptionId}` (`UNIQUE`), at most one financial task per redemption. Policy switches per queue: `refundIfRemovedWhileCalled` (default true), `refundOnNoShow` (default false), `refundIfViewerLeavesCalled` (default false; domain name `refundIfViewerLeavesWhileCalled`).

| From → to | Triggered by | Financial decision (redemption source) | Notes |
|---|---|---|---|
| waiting → called | panel `/call`, `/transitions`; chat `proximo` | none | |
| waiting → removed | panel, moderator `remover`, viewer `sair` | **cancel, always** | |
| called → in_progress | panel, chat `atender` | **fulfill** (points consumed for good) | |
| called → completed (direct) | panel `to=completed`, chat `concluir` (moderator) | **fulfill** | No question, no group concept (P1-2) |
| called → removed | panel / moderator | cancel only if `refundIfRemovedWhileCalled` | switch off: nothing, stays `UNFULFILLED` (R2) |
| called → removed | viewer `sair` | cancel only if `refundIfViewerLeavesCalled` | default off: stays `UNFULFILLED` (R2) |
| called → no_show | panel, timer | cancel only if `refundOnNoShow` | default off: stays `UNFULFILLED` (R2) |
| in_progress → completed | panel, chat `concluir` | none (fulfill already exists; guard `:2303-2308`) | |
| in_progress → removed (normal) | panel / moderator / viewer | none (guard turns cancel into no-op) | |
| any active → removed, reason `queue_cleared` / `queue_deleted` | clear (panel, chat `limpar`), delete | **cancel, always** (overrides the policy) | **Correction:** with an `in_progress` entry (fulfill exists) the first delete pass and the clear raise on the `UNIQUE` key and roll back the whole operation (W3-1). The delete re-entry pass is guarded |
| active → completed / removed, `origin=external` | EventSub update, reconciliation | none (mirrors the remote) | |
| any transition of a `manual` entry | n/a | none | |

No path returns to `waiting`. No "member" concept exists anywhere in `apps/api/src` or in the schema.

### 6.3 Queue deletion and the worker

1. `requestQueueDeletion`: queue without reward or converted to local → deleted at once. With reward → `deleting`, active entries → `removed/queue_deleted` with cancel (first pass unguarded), reward paused, task `reward.delete`.
2. `processDeleteTask` (`reward-worker.mjs:256-338`): reads the reward; lists Twitch `UNFULFILLED` **twice**; for each one without a financial task, `recordQueueDeletionRedemptions` writes `expected_status = CANCELED` and creates `redemption.cancel` **without reading any policy or entry state** (passes over existing `fulfill`, re-arms a contradicted `resolved_manual`). Blockers: `pending|retry|processing` = wait 30 s; `unknown|conflict|failed` = "blocked by review", recheck 5 min; 401 = authorization required.
3. **Correction:** an exception in step 2 is not caught; the task stays `processing`, is re-claimed every 30 s with `attempts` growing, with no ceiling and no visible state (W3-3).
4. `conflict` and `failed` have no manual exit, so one of them blocks the deletion forever (W3-2).

### 6.4 Financial worker (unchanged, sound)

Claim with `FOR UPDATE SKIP LOCKED` and a 30 s lease; every attempt starts with a **read** of the remote status; writes only when the read says `UNFULFILLED`; an answer without confirmation is re-read; 401 → `unknown(authorization_required)`; 404 → retry, never confirm; permanent 4xx → `failed`; 429 respects `Retry-After`; 6 attempts per cycle (1/4/16/60/60 min, jitter 0.8-1.2); confirms only when the remote equals the expected status. `lastError` keeps only a cut code; logs go through an allowlist. Exception to the lock order: `retryOutboxManually` (W3-5).
